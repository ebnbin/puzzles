# 按键适配进度

四十个谜题，一个一个把「在键盘上能做、在触摸屏上做不到」的事补成按钮。这份文档记录每个
游戏读哪些键、哪些已经有落点、还差什么。

**第 1 类（光标伴生）已经走完四十个。** 剩下的都是第 2 类的零头，列在「总览」下面。

改动落地时同步改这里。**这不是生成物**，没有脚本会替你更新它。

## 判据

两条线，先后关系不能颠倒。

**第一条（keys.ts 一开始就写着的）：一个键值得做成按钮，当且仅当它做的那件事没有任何手势
能做到。** 不是「有用」，不是「常用」，是「够不着」。Net 的重排（`J`）进来了，因为
`net.c` 自己在源码里问「should we have some mouse control for this?」而答案是没有；Net 的
右转没进来，因为点一下棋盘就能做到。

**第二条（方向键之后加的）：按键分两类。**

- **第 1 类，光标伴生。** 作用取决于光标在哪。没有它们，方向键把光标移过去了也做不了任何
  事——方向键就是装饰。绝大多数是 `Enter` 和 `Space`，也就是 midend 翻译过的
  `CURSOR_SELECT` / `CURSOR_SELECT2`（midend.c:1255）。
- **第 2 类，独立键。** 作用和光标无关（整盘操作、显示开关、提示）。有没有方向键它都有用，
  也都同样够不着。

第 1 类只在方向键开着时有意义，所以它们和方向键同一个块、同一个开关；第 2 类归键盘
（`keys.ts` 的 `RULES`），和方向键无关。

**第二条会放宽第一条，这一点以前没写清楚。** 第 1 类的键很多是「够得着」的——Net 的左转点
一下棋盘就能做，Twiddle 的两个方向点一下和长按就能做，Sixteen 在边框上推一行也是。按第一条
的字面，它们一个都不该有按钮。但第一条问的是「这个**走子**够不够得着」，而第 1 类要回答的是
另一个问题：**方向键把光标移过去之后，有没有东西可按**。没有的话方向键就是个装饰，而装饰
本身是我们加的，不是上游的。

所以准确的说法是：**第 2 类严格按第一条判（走子够不着才给按钮）；第 1 类按「方向键开着时，
这个键是不是让光标有意义所必需的」判。** Twiddle 是最干净的例子——两个键一个新走子都不带来，
但少了它们，那个会走来走去的外框方块就是个没用的记号。

### 还有第三条，是 sixteen 逼出来的：够得着不等于看得懂

Sixteen 的边框那一档曾经被这两条判掉过：同两个键在边框上是「推一行」，那是纯粹的走子，而它
够得着（点边框箭头，`BORDER` 就是 `TILE_SIZE`，实测 390px 手机上是 **65×65 CSS px**，很好按），
也不是光标存在的理由。**结论是那一档不给按钮，光标干脆不去那里**——一个方向键把光标带出去，
就立刻发一个反向键把它拉回来。

**这条判断是错的，而错处不在推理，在于问错了问题。** 两条判据问的都是「这么改能多做到什么」，
从来没问「现在这套读者能不能看懂」。判据是用来决定**加什么**的，不是用来强迫保留一个看不懂的
东西的。

看棋盘就知道差在哪：

- **光标停在边框上**，上游会把那一圈胖箭头里的一个点亮成白色。按一下 = 那一行按箭头指的方向
  走。**没有一个新概念要学。**
- **光标停在格子上**，上游只把那个数字涂深一点。它说的是「选中了这一格」——而这句话本身什么
  都不说明。读者还得知道：按下 `Enter` 之后，四个方向键会**改变含义**。
- 而那个模式**在棋盘上完全不可见**。实测：开着锁定和不开锁定的两张棋盘截图**逐字节相同**
  （`cur_mode` 在 `game_redraw` 里一次都没出现，sixteen.c:569）。唯一的指示是我们自己那个
  按钮的按下态。

所以现在的做法是**完全跟随上游**：光标想去哪去哪，两个功能键就是上游的 `Enter` 和 `Space`，
**脸跟着位置换**——边框上是「推这一行」和「反方向推」，格子上是两个粘滞锁定。四张脸全都在，
一个上游能力都没有拿掉，那段拉回光标的代码也删了。

一句话：**第 1 类的键要跟着上游的光标走，而不是把光标赶到我们挑的地方去。**

**跟着走之后，图标要说的是「这个键现在是什么」，而不是「按下去会怎样」。** 这一条是 sixteen
的四张脸逼出来的三个具体教训，都值得记：

- **锁就画锁。** 格子上那两个键原来画的是「方块 + 箭头」——那是**按下之后的后果**，于是摆在两个
  真的会推行的键旁边，读起来像第三种推法。它们本身是锁，现在就是两把挂锁，靠锁里那个方块的
  填充/空心区分「锁方块」和「锁位置」。
- **状态要看得见，就得给它足够的尺寸。** 挂锁最早是贴在方块角上的一个小徽章，20px 下锁梁整个
  糊死；第二版把锁缩到方块旁边当配角，开和闭只差一两个像素——**而开闭正是这两个键存在的理由**。
  最后是反过来：锁占满整个字形，方块缩成锁体里的一个记号。**谁是主角由「哪一半必须看得清」决定。**
- **判断不出来的东西，图标里就一点都不能有。** 边框那对改了两次才对。上游在四条边上报的是同一个
  词（`Slide` / `Back`），指的是那条边上箭头的方向，而**这一侧根本不知道光标在哪条边**（要知道
  就得自己存一份上游的光标，为一个图标不值）。所以：
  - 第一版是「一排瓦片被推着走」和它的左右镜像（netslide 当时用的那张图）——上下两条边上直接
    说错了轴。
  - 第二版是「棋盘那个胖箭头 + 一支顺着/逆着它的小箭头」，理由是「上半只是排版」。**这条理由
    不成立**：画出来的箭头就是会指，而指就是含义。上下边上它一口气说了两次「右」。
  - 第三版是一对旋转的环，理由是「推一行本来就是这一行的循环」——`(cx - dx + w) % w`，这话没
    错。但**读者看到的是一行横着滑过去**，绕回来只是末端的一个细节，手册自己的词也是 slide。
    环不是因为它描述了 sixteen 才被选中的，是因为「排除方向之后，不带方向的互逆几乎只剩旋转」
    ——那是**在约束下搜索**，不是设计。
  - 第四版是**一个方块里画 `+`，一个方块里画 `−`**：一步推过去，一步拉回来，正是上游写下的
    那步棋（`R{y},+1` / `R{y},-1`），不是比喻。它死于下面那次普查——`plusSquare` /
    `minusSquare` 是 magnets 的两极，画法相差不到半个单位。
  - 现在是**一个点 / 两个点**：这是第一个键，那是第二个键。到此为止。

  **图标的信息量应该正好等于我们的认知量。** 前四版都是在回答「这两个键做什么」，而这一侧对
  它们的全部认知只有「一对互逆操作」——不知道是哪条边、哪个轴、哪个方向。第四版已经压到只说
  「一步 / 退一步」，仍然多了一点：连「一步」都是从走子里读出来的，图上说不出「往哪」。点数
  说的是**这个键在这一对里排第几**,而这件事这一侧百分之百确定。反过来说：**当这一侧答不出某个
  量时，图标里出现那个量就是在瞎猜**，而猜错的那一半比不画更糟——不画只是没说，画错是说反了。

  **动词没有丢，它在文案里。** 按钮仍然说 "Push this line along the arrow" / "Pull this line
  back"。图管排位，词管动作,两边各说各擅长的那一半——这和 push/pull 当初被从图里赶到词里是同一
  笔账。

### 换图标之前先普查一遍已经被占的形状

第四版是被这次普查杀掉的，而它本可以更早被杀掉——`+`/`−` 和 magnets 撞脸这件事，从加上它那天
起就成立，只是没人查。把 `Icon.tsx` 里所有被游戏键用到的字形（59 张）按「新图标会挨着谁」排一
遍，结论是三片邻居已经满了：

| 形状 | 已经是谁 | 拥挤程度 |
| --- | --- | --- |
| 整块圆角方，实心 / 空心 | `black` / `white` = 填了的格 / 空格 | 9 个游戏，全文件最挤 |
| 方框里放一个记号 | `dotSquare` `circleSquare` `plusSquare` `minusSquare` `crossSquare` `questionSquare` `emptyCell` | 七张，加上第四版自己就是九张 |
| 实心圆套一个环 | `islandDone` = bridges 的「这座岛连够了」 | 一张，但形状唯一，撞上就是撞死 |
| 裸的勾 / 裸的叉 | `done` = 确认（8 个游戏）/ `cancel` = 放弃（5 个） | 已经是这个文件的两个通用词 |

**候选里死掉的那几个，全是这张表的直接后果**：填充/空心方是 `black`/`white`；方框里放点、放圈
是 `dotSquare`/`circleSquare`；靶心是 `islandDone`。真正还空着的只有三片——键盘键符号
（`⏎`/`␣`，全文件零个）、菱形、裸弧线——加上「一个点 / 两个点」：`cycle` 把四个点摆成环、
`stipple` 把五个点摆进方框，但一个和两个并排放着，没人用过。

**这条以后照做：加字形之前先跑一遍这个普查。** 撞脸不会有任何东西报错，`tsc` 管不着，
`verify-palette` 也管不着——它只会让两个游戏里意思完全无关的两个键长成一个样，而且是在不同的
屏幕上，谁都不会同时看见，所以没有人会发现。

  （push / pull 试过，两轮九种：手掌顶着方块 vs 钩子勾住、平板 vs 爪、远 vs 近、小 vs 大、门把
  手推进去 vs 拉出来、弹簧压缩 vs 拉伸。**20px 下没有一个活下来**，而且全都是同一种死法：推和拉
  的区别是一个握法、一道缝、一圈弹簧，20px 放不下这么小的特征，两个图看上去一模一样。动词是好
  动词，所以搬到文案里去了——那里有地方。另外否掉的：环形和 `restart`/`rotate`/twiddle 那一对
  撞脸；双人字号 `>>` / `><` 太抽象；实心三角读成播放；一行方块旁边挂个加号 20px 下糊成一团。）

（顺带记两个查证过的事实，省得下次重问。一、**sixteen 的边框上是两个键，不是一个**，跟
netslide 不一样，差别只有一行 C：netslide 的反向条件是 `if (button == RIGHT_BUTTON)`
（netslide.c:1115），所以它两个键报同一个词、一个按钮就够；sixteen 的是
`if (button == RIGHT_BUTTON || button == CURSOR_SELECT2)`（sixteen.c:725），`Space` 推的是
**反方向**，标签照实说了 `Slide` 和 `Back`。二、**两套走子完全相同**——边框那一档产生
`R{y},±1` / `C{x},±1`，棋盘上开着锁定模式产生的是同一批（sixteen.c:670-680）。所以这次改动
改的从头到尾都不是能做什么，是看不看得懂。）

**netslide 的那一个键用的是同一张 `primary`，而共用是目的不是省事。** 它做的是同一件事、站在
同一圈边框上、对「光标在哪条边」同样一无所知；同一个动作画两张图，本身就在声称它们不一样。它
原来那张图指着右边，四次里对一次——方向只由 `interpret_move` 从边框推出来（netslide.c:1097），
而 `encode_ui` 是 `NULL`（netslide.c:1867），光标连存档里都没有，这一侧推不出来。

**它旁边没有 `secondary`，这不是缺口，是信息。** sixteen 的两个键是一对互逆，netslide 的键盘上
只有一步推——上面那行 C 的差别就是这个。反向推它也有，但只在右键上，而**触摸早就够得着**：长按默认
就是右键（`usePuzzlePointer.ts` 的 `hold`），`HOLD_BUTTON` 是把长按花在别处的那些游戏的名单，
里面只有 net。所以这里既不欠一个按钮，也不欠一条 `HOLD_BUTTON`——往那张名单里写一条和默认值
相同的记录，只会让名单本身开始说谎。

## 现在的形状

方向键是每个游戏一个偏好设置，默认关（`puzzles.arrows`，见 `useArrows.ts`）。开启后棋盘下方
出现一个 3 列的块：

```
[ 第1类 ]  ⬆️  [ 第1类 ]        八向的游戏：  ↖ ⬆️ ↗
    ⬅️     ⬇️     ➡️                          ⬅️    ➡️
                                              ↙ ⬇️ ↘
```

十字上排左右两格给这个游戏的第 1 类按键，最多两个（`keys.ts` 的 `CURSOR_KEYS`）。八向的
游戏（只有 Inertia）拿这两格放对角，所以**八向和第 1 类按键放不下同一个块**——真撞上了再说，
现在没有游戏两者都要。

## 全表

实现了 `current_key_label`，会按当前光标位置返回一个活的词。五个没实现（`NULL`）：cube、
fifteen、loopy 三个本来就不读这两个键，**untangle 和 palisade 读但不报**——这两个也都做完了，
词是我们自己起的，见「后端一个字都不报的两个」。

## 遗留问题

四十个游戏走完之后剩下的账，一处集中。分四类不是为了好看：**「还没做」「做不了」「做了但有
代价」「以后会安静地坏掉」是四件不同的事**，混在一起就没法判断该先动哪一条。

每条都写「卡在哪」。一条没有卡点的遗留问题，说明它其实是没做，应该直接做掉。

### 一、缺一个机制，不是缺一次改动

这些都通过了判据一（够不着），也知道该长什么样，但每一条都要先有一样现在没有的东西。

**中键曾经在这张表上，现在不在了。** 五个用中键的游戏一个一个查完，没有一个真的够不着——最后
一条 loopy 是查了四次才落地的（见「三件跨游戏的事」）。**一条挂了很久没人动的遗留问题，第一步
永远是重新验一遍它还成不成立**，而不是直接去做。

| 谁 | 什么 | 卡在哪 |
| --- | --- | --- |
| 九个游戏的修饰键组合 | net 移原点/源、pattern 拖着刷、tents 拖一行、bridges 画桥、unequal 和 towers 划线索、range、pearl 画线、palisade 画墙 | 要先有一个**修饰键开关**。它天然属于第 1 类，但做不成一个普通按钮 |
| signpost 的 `X` | 把整条链一起拆开 | 要一次**右键拖拽**。而触摸上的长按是「按下和抬起一起发」（`usePuzzlePointer` 里那句「现在没有什么可拖的」），所以长按永远变不成拖拽。鼠标能做，手指不能 |
| galaxies 的 `h` | 走一步显然推理（`solver_obvious`，galaxies.c:2888） | 要在**键盘那一排**加一个键。它是唯一一个有实质提示、却连键盘都没有的游戏 |
| map 的 `l` | 显示区域编号（map.c:2500） | 同上，一个显示开关 |
| bridges 的 `g` | 提示显示开关（bridges.c:2589） | 同上 |

**修饰键那条有一个便宜的出口，先查它。** sixteen 是这一行里唯一解决了的，办法是上游自己给的
——它的手册写着 `Enter` 模拟按住 Ctrl、`Space` 模拟按住 Shift，也就是上游把修饰键做成了粘滞
开关，而粘滞开关就是一个按钮。轮到别的游戏时先翻一遍它那一章：**一个现成的粘滞版本，比造一个
修饰键开关便宜得多。**

### 二、待定一处：inertia 的 `Advance`

只有一处真正悬着，而它悬着的理由这次才说清楚。

flood 的 `Advance`（重放求解器下一步）这次拿到了按钮，因为它是第 1 类的邻居——flood 有光标，
所以十字上排那两格是它的。**inertia 的同名键拿不到同一个位置**：它是全集唯一的八向游戏，那两
格已经拿去放对角了（见「现在的形状」）。所以它只剩键盘那一排，也就和上面 galaxies 的 `h`
变成同一件活。

判据上它够得着吗？够不着——求解器的重放没有任何手势。但它**只在按过求解之后才有用**，而按过
求解的局已经不是在解了。所以这一条不是技术问题，是要不要给「看答案」一个常驻按钮的问题。

### 三、明知有代价，选择了不修

这几条都量过，也都写下了不修的理由。列在这里是为了**下次不要重新发现一遍**。

| 谁 | 代价 | 为什么不修 |
| --- | --- | --- |
| palisade | 一半的按键是空按——实测走 26 步按 26 次，13 次什么都没发生 | 要修就得自己记住光标的奇偶，而点棋盘会把光标扔到任意位置，那份副本立刻就漂——正是「加一条之前」三条判据里「失败能自愈」不成立的样子 |
| blackbox 角上的「检查」 | 理论上存在按钮亮着而按下去无事发生的一刻 | 走不到：方向键不让光标进那个角，唯一能改变球数又不收起光标的路只有物理键盘 |
| netslide / sixteen 的边框 | 光标在边框上时，四个方向键只有两个是活的，看起来像 bug | 上游键盘本来就这样，而且标签在整圈上报同一个词，分不出光标在哪条边——**没有依据置灰** |
| mines 的 `Enter` | 亮 ≠ 安全：旗插错了它照样亮、照样能按，按下去会踩雷 | 风险是这步棋本身的，点一下那个数字承担的完全相同。但记住：**一个亮着的按钮比一次点击更像一种背书** |

### 四、会安静地坏掉的四处

这一类最值得单独列：**它们坏掉的时候不会有任何东西报错**，`npm run build` 照样绿。

1. **`key()` 的返回值只对一个键有效。** guess 的 `⌫` 能向后删，靠的是后端在「这个键认识但没
   效果」时返回 false——而 emcc.c:456 只对拼作 `Backspace` 的键这么做，本来是给 KaiOS 的一个
   照顾。上游哪天删掉那个分支，这个键就悄悄退回上游语义（删光标所在那格），**没有任何报错**。
2. **`lsk === csk` 的抹空。** 两个键报同一个词时上游把第一个抹成空串，所以「空」和「被抹掉的」
   从这一侧分不出来。`BOTH` 那张表是唯一的解药，而它是手写的。**每加一个用 `faces` 的游戏，都
   要先把它 `current_key_label` 的所有分支列一遍**，看两个键能不能同时给出同一个非空词。漏了不
   会报错，只会让一个按钮说它能做一件它做不了的事——dominosa 上就是这么现的形。
3. **八向和第 1 类肩键放不下同一个块。** 现在没撞上，因为唯一的八向游戏 inertia 没有第 1 类
   键。上面第二类那条一旦要做，就正好撞上——这两条是同一件事的两面。
4. **这一块没有提交进仓库的自动检查。** `npm run build` 里只有 `tsc --noEmit`，而这一块的正确
   性是「按钮的死活和后端说的对不对得上」，只有真跑引擎才验得了。所有验证都是临时写的
   playwright 脚本，跑完就扔——和 `marks/` 是同一笔交易，理由也一样：要起 vite preview，而
   playwright 不在 `package.json` 里。**改这一块就得自己搭一次，别只信 build 绿了。**

### 五、这份文档自己

**不是生成物，没有脚本会更新它。** 这一节的每一条都是手写的，也只能手写掉。已经因此错过三次
数（见「三件跨游戏的事」和「那份『其余 7 个候选』的名单是错的」），三次都是**拿 grep 当阅读**。

## 三件跨游戏的事

**37 个读 `Enter`，37 个也读 `Space`——但只有 31 个给了 `Space` 自己的含义。** 另外 6 个
（netslide、flip、pegs、inertia、unequal、galaxies）用 `IS_CURSOR_SELECT` 宏一次覆盖两个键，
进去之后不再分，两个键报同一个词，所以在那 6 个里 `Space` 只是 `Enter` 的同义词。只有 Cube、
Fifteen、Loopy 三个两个都不读。

这条数错过两次，两次都是拿 grep 当阅读。第一次：审计脚本只找字面的 `CURSOR_SELECT2`，把用宏
的漏掉了，于是「29 个读 Space」变成一句听起来精确的错话。第二次是补救时矫枉过正——**用了宏不
等于两个键是同义词**。magnets 和 signpost 拿它当门卫（`if (IS_CURSOR_SELECT(button))`），进门
第一件事就是 `button == CURSOR_SELECT` 分岔：magnets 的 `Enter` 走 `+`/`−`/清除，`Space` 走
`?`/`X`；signpost 是「连到下一格」和「连到上一格」。它们各自该有两个按钮，表里也是两个。要问
的从来只有一件事：这个 `current_key_label` 读不读 `button`——两种写法都得找，找到之后还得往下
读一行。

这两个键现在全部补齐了。回头看，**`Space` 值不值得第二个按钮，最后落在三种答案上**：

- **是同义词，只给一个键**——netslide、flip、pegs、galaxies、unequal 五个走
  `IS_CURSOR_SELECT` 宏之后不再分岔，两个键报同一个词，第二个按钮会是第一个的复制；另外四个
  铅笔游戏（solo、keen、towers、undead）里 `Space` 和 `\b` 走同一条分支，就是「清除」，键盘上
  已有 `⌫`。上面数出来的第六个同义词 inertia 不在这条里：它压根没有光标，两个键都不长在方向键
  旁边。
- **不同但没用，也不给**——这一档现在是空的。它原来只有 samegame 一个：四种局面里只有一种两个
  键不同，而那点不同（取消选中）玩下去一次都用不上。**这条判据本身是错的，见「samegame 的取消
  选中」那节**——「没用」不是判据，「上游键盘上有没有」才是。
- **不同而且有用，给**——其余全部。判据就是那一行：`labels.space !== ''` 恰好等于「两个键
  不同」，白送的。

**修饰键组合没有落点，也没打算给。** net（移原点/源）、pattern（拖着刷）、tents
（拖一行）、bridges（画桥）、unequal、towers（划线索）、range、pearl（画线）、palisade 都读
`Shift`/`Ctrl` + 方向键。它们天然属于第 1 类，但做不成一个普通按钮——得先有个修饰键开关。
单独记在这里，不混进上表。

**Sixteen 是这条里唯一一个已经解决的，办法是上游自己给的。** 它的手册写着「pressing Enter
simulates holding down Control（press Enter again to release），while pressing Space simulates
holding down Shift」——上游自己把这两个修饰键做成了粘滞开关，而粘滞开关就是一个按钮。轮到
上面别的游戏时先查一遍有没有同样的东西：一个粘滞版本比「加一个修饰键开关」便宜得多。

**中键这笔账，最后一条也销掉了——五个用中键的游戏没有一个真的够不着。**

中键就是鼠标滚轮那一下（`emcc.c:321` 把 JS 的 button 0/1/2 映成 `LEFT`/`MIDDLE`/`RIGHT`）。
桌面上它本来就通得过去，`usePuzzlePointer` 还额外把 **Shift+点击**也当成中键（那句注释写着
「Shift 是明确在要中键」）。**手指上只有两下**：点是 button 0，长按是「第二下」，而第二下算哪个
按钮由每个游戏自己说——`HOLD_BUTTON` 里只有一条，net 的长按就是中键（只管长按，鼠标不受影响，见下）。

| 游戏 | 中键做什么 | 手指够得着吗 |
| --- | --- | --- |
| net | 锁定/解锁一块 tile | ✅ 长按就是中键，`HOLD_BUTTON` 唯一的一条 |
| mines | 连开，而且在盖着的格子上也强制半径 1 | ✅ 点已翻开的数字本来就是连开，见下一条 |
| unruly | 直接把格子设为「空」 | ✅ 两个光标键之间走两步就到 |
| pattern | 拖着刷成「未定」（灰） | ⚠️ 单格已经到了（第三个按钮）；**成片刷**仍然要中键拖拽 |
| loopy | 把一条边设为「未知」 | ✅ 点一下已经画上的线就是它 |

**loopy 那条是最后查出来的，而它一直被记成「无解」。** 它的边有三态：未知 / 有线 / 划叉。左键
未知→有线、有线→**未知**、叉→**未知**；右键未知→叉、叉→**未知**、有线→**未知**；中键则是从任何
一态直接回到未知。两条 `switch` 里的 fallthrough（loopy.c:3084、3102）意味着**左右键本来就各自
能到未知**，中键一件新事都不做。那两条 fallthrough 上面各有一个 `if (stylus)` 拦着，而 `stylus`
来自 `MOD_STYLUS`，只在编译时定义了 `STYLUS_BASED` 才置位——那是 WinCE 时代的宏，这个 build
从没定义过。

实测（手指，长按 700ms 当右键）：`6y` → `6u` → `6n` → `6u`。点两下就回到未知，和中键一模一样。

**上游确实有一套「只有一个按钮」的适配，而它在这个 build 里是死代码。** 这条要写清楚，因为
「上游本来就处理了，不该由我们在下游手动做」是一个很自然、也确实成立过的怀疑。

叫 `MOD_STYLUS`。五个游戏读它，正好就是声明了 `STYLUS_SUPPORT` 的那五个，含义在五个里完全
一致：**让一个按钮循环走完所有状态，而不是每个按钮设一个绝对值**——因为触笔平台只有一个按钮。

| 游戏 | 没有 stylus（也就是我们这一档） | 有 stylus 会变成 |
| --- | --- | --- |
| net | 左=左转，右=右转，中=锁 | **右键改成锁**（net.c:2299） |
| loopy | 左：未知→线、线→未知；右：未知→叉、叉→未知 | 左：未知→线→叉→未知（三循环），右反向 |
| pattern | 左=涂黑、右=涂空、中=灰，三个绝对值 | 左右各是一个三循环，**灰顺手就到** |
| lightup | 左只放灯（撞上「不可能」标记就拒绝），右只放标记 | 两个键各自在灯和标记之间切换 |
| tents | 左：空↔帐篷；右：空↔草 | 各自三循环 |

**为什么够不着：它是编译期的，而且没人定义它。** `stylus` 来自 `button & MOD_STYLUS`，而
`MOD_STYLUS` 只有 `midend.c:991` 一处会置位，外面包着 `#ifdef STYLUS_BASED`。`STYLUS_BASED`
在整个上游树里出现三次（net.c:31、gtk.c:1894、midend.c:991），**定义它的地方一处都没有**
——没有 CMake、没有构建脚本、没有命令行。它是 Palm / PocketPC 时代的平台宏。

**而且它不是「触摸」开关，是「这台机器的指针只有一个按钮」开关。** 一个 wasm 二进制同时服务
鼠标和手指，这句话没法说：桌面读者有真的右键，开了它就把右键也换成循环。

**net 那条还额外贵。** `net.c:31-33` 里 `STYLUS_BASED` 会顺带定义 `USE_DRAGGING`，把 net 的整个
鼠标模型从「点一下转一格」换成「拖着转」——上游自己的注释写着他们在 Mac 上试过，
"found it to be quite strange and unintuitive"。

**第二层，也是更直接的一层：上游自己的 web 构建根本没有触摸代码。** `emccpre.js` 只挂
`onmousedown` / `onmousemove` / `onmouseup`（外加一个只用来 `setPointerCapture` 的
`pointerdown`），约定是 Shift+点击=中键、Ctrl+点击=右键——我们照抄的就是这一套。**手机上一根手指
在上游那份构建里只能产生左键**，长按这个概念是这一侧发明的。所以 `HOLD_BUTTON` 不是在重复
上游做过的事，是在做上游的 web 构建没做的事。

而它做的事和 stylus 分支**结果一模一样**，只是走了另一个还活着的按钮：

```c
action = (button == LEFT_BUTTON ? ROTATE_LEFT :
          stylus ? TOGGLE_LOCK :                                 /* 死的 */
          button == RIGHT_BUTTON ? ROTATE_RIGHT : TOGGLE_LOCK);  /* ← 我们落在这里 */
```

**影响范围：另外四个游戏的 stylus 分支同样是死的**，各自的后果不一样：

- **loopy**：正因为 stylus 死了，左右键才会各自 fallthrough 回「未知」——上面那条「中键是多余
  的」整个建立在这上面。stylus 一旦开着，那两个 `if (stylus)` 就把 fallthrough 拦住，结论**反
  过来**，中键会重新变成唯一一条直达未知的路。
- **pattern**：灰（未定）在 stylus 下随便哪个键循环两下就到。这曾经是我们那笔「灰色丢了」的
  账，现在两边都到了——我们给了它第三个按钮，而 stylus 那条路仍然是**上游有过答案、只是编译掉
  了**。
- **lightup**、**tents**：非 stylus 的绝对语义，两个光标键都已经覆盖，没有欠账。

**结论：不需要改 C，但这件事让 `HOLD_BUTTON` 的边界挪了一次。** 它原来同时管长按和鼠标右键，
理由是「长按和右键是同一个请求的两种说法，答得不一样会让鼠标和手指对同一块棋盘各说各的」。
**这条理由是错的，而错在一个具体的地方：两种指针的家当不一样。** 手指只有两下；鼠标有三个键
外加两个修饰键，滚轮和 Shift+点击**本来就到得了中键**。所以 net 那笔交易——拿右键换锁定——是
手指非做不可、鼠标做了纯亏的：亏掉的是右转，而右转在鼠标上从此**一个手势都没有**。

现在分开了：**`HOLD_BUTTON` 只管长按，鼠标一律照上游原样走**（Shift=中键、Ctrl=右键、其余直
通，`emccpre.js:360-365`）。两者只在一处不一致，而那一处正是硬件不一致的地方；其余三十九个
游戏的 `HOLD_BUTTON` 都是右键，长按和右键仍然是同一件事。

实测 net 的七个手势：

```
鼠标 左键        -> A  左转          手指 点   -> A  左转
鼠标 右键        -> C  右转          手指 长按 -> L  锁定
鼠标 中键        -> L  锁定
鼠标 Shift+左键  -> L  锁定
鼠标 Ctrl+左键   -> C  右转
```

（`A`/`C`/`L` 是 net 自己的走子字母，net.c:2340，所以存档直接就说清了每个手势落到哪个动作。）
另外抽查了 mines 和 pattern 的右键——`F4,4` 和 `E4,4,1,1`，和改之前一样：net 是
`HOLD_BUTTON` 里唯一一条，别的游戏鼠标那半边一个字节都没动。

**还要留意 loopy 那条**：它的结论依赖 stylus 是关的，哪天升级上游前先确认这一点没变。

**mines 曾经记在这张欠账单上，那是记错了。** 这里写过「中键连开够不着」——但
`ui->hradius = (grid[cy*w+cx] >= 0 ? 1 : 0)`，而 `LEFT_BUTTON` 把它抄进 `validradius`
（mines.c:2616-2619），格子已翻开时就是 1，松手走 `uncover`。**点一下已翻开的数字，本来就是
连开**，手册也直说：「If you left-click in an *uncovered* square, it will clear around the
square.」中键唯一多出来的是它在盖着的格子上也强制 `validradius = 1`，于是不会误翻——那是个
安全变体，不是一项能力。

教训是通用的：**看见一个键/按钮映射到某个动作，不等于那个动作只有它能做。** 要判断「够不着」
得把每一条产生同一步棋的路都走一遍，而不是找到一条就下结论。guess 的颜色键是同一个错误的第二
次，见「guess 的颜色键」——**两次都是只读了 `interpret_move` 里键盘那半边。**

**同一节里还有第三种走神，值得单列：把「读不到」当成「办不到」。** guess 的颜色圈位置确实读不
出来，于是那条不一致被记成了遗留问题；可让它到指定位置根本不需要读——`move_cursor` 的夹边行为
就能从任意起点走到已知位置。netslide 的方向是同一个形状（那次结论对，因为方向连推都推不出来）。
**下次写下「读不到所以做不到」之前，先问一句：能不能不读就把它推到一个已知的地方。**

**第三次是 signpost 的 `x`，而这次连它做什么都写错了。** 表里曾经写着「`x` 标记不可能⬜」。
它其实是**把这一格从链条里拆出来**，而且够得着：`interpret_move` 在一次拖拽**松手在棋盘外面**
时发出的是同一条 `C` 走子（signpost.c:1592）。实测——拖出棋盘下沿松手，存档里出现 `C0,0`，和
按 `x` 一模一样。同一段代码里紧挨着的 `X`（拆整条链）反倒是真够不着的，因为它要一次右键**拖
拽**，而触摸上的长按是按下和抬起一起发，永远变不成拖拽。**同一个键的两种写法，一个够得着一个
够不着**，只读键盘那半边会把两个都判错。

**第四次是 loopy 的中键，而这次错的时间最长。** 它从这份文档第一版起就写着「没有落点，无解」，
而左键点一下已经画上的线就回到未知，一模一样。这次的错法和前三次不同：不是漏读了鼠标那半边，
是**漏读了 `switch` 的 fallthrough**——`case LINE_YES:` 底下没有 `break`，就掉进
`case LINE_NO:` 的 `button_char = 'u'`。C 的这个特性正是「读代码」和「看代码长什么样」的分界。

四次合起来的规矩：**判一件事「够不着」之前，把 `interpret_move` 整个读完**——键盘那半边、鼠标
那半边、拖拽的松手分支、`switch` 掉下去的地方。四次里有三次，那条够得着的路就在同一个函数里，
离写错的那条不到五十行。

**pattern 在这条账上来回过两次，值得整段记下来。** 灰色（未定）原本只有中键或 Shift+点击能
到，两个光标键刚加上时是上游的循环（`Enter` 灰→黑→白，`Space` 反向），循环总要经过第三态，
所以顺带就把灰补上了。第二步改成绝对语义（`does`），两个键各要一个颜色，谁都不要「Grey」，
那格又还回去了——当时记成「已知代价」。第三步是把循环搬回来。

**代价那一栏当时算漏了一项：不是「暂时靠撤销」，是根本回不去。** 实测按钮只会吐出 `F` 和
`E`，永远没有 `U`；手指轻点是黑、长按是白（长按默认就是右键）；方向键发的是不带修饰的键，所以
`Ctrl+Shift+方向` 也不在。三条路一条都不通，而撤销会把这一步之外的东西一起收回。**「已知代价」
这四个字当时掩盖的是一个没查过的事实**——查的方法只是把按钮按到底、看存档里出来的走子。

第三步是把上游的循环搬回来。每个状态都一步可达了，代价换成「两个按钮都没有固定含义」：想涂黑
的时候按钮在左还是在右会变。这不是理论上的不便——pattern 是靠连着刷一长条来玩的，按钮在重复按
压之下会动，是一种**方向不对的真实**：忠实于后端，却把学习成本转嫁给读者。

第四步同时拿到两样：**三个键，各自一个颜色，恒定不换脸**，靠 `does` 把上游的两个循环键翻过来。
花掉的只有一行高度——键盘从两行变三行，走的是 Inertia 那个九宫格的同一笔账（`[data-keys='3']`），
横屏 rail 依赖的宽度没动，实测三行块 128×128，和 Inertia 一样。

**而这三个键不置灰，是这条规则在全 app 唯一的例外（`lit`）。** 置灰是家规，别处都对：按不动的
按钮应该说出来，而不是把按键吞掉。这里不对，理由只有在「怎么玩」里才看得见——pattern 是把一长
条格子一口气刷成同一个颜色，中间夹着几格本来就是那个颜色，**按钮在刷到一半时自己熄灭，是在拇
指没看它的时候改变形状**，这比省下的那一次空按更糟。

还有一层：这里的空按不是失败的按。在已经是黑的格子上要黑，格子刷完还是黑的——**后置条件成立，
按钮把事办了，没什么可报告的**。这是幂等，不是无效，也正是这条例外推广不出去的原因：别的地方
一个按不动的键意味着读者想要一件事而没得到。

实测三种状态各按一次自己那个键：走子数不变，而且**引擎写出的存档逐字节相同**。

**中间那个看着最自然的折中不成立，记下来免得再想一遍**：左键固定「黑」、只让右键循环，在**白
格**上会退化——白格上 `Enter` 报 `Grey`、`Space` 报 `Black`，所以 `does: 'Black'` 解析出来的也是
`Space`，两个按钮发同一个键、给同一个颜色、戴同一张脸。

顺带一条经验，也是从这里来的：**一个游戏的「循环键」往往就把它的中键那格顺手补上了**，反过来
说，把循环键改成绝对键就会把那格再丢掉。slant、mosaic、unruly、singles、range、tents、lightup
后来都按「照着标签走」做了——**没有一个改成绝对语义**，所以那格都顺手补上了：unruly 的中键
「设为空」在两个键之间走两步就到，pattern 丢掉的那格是唯一一次例外，理由写在上面。

**这一批七个是最便宜的一批，理由值得记：它们的标签说的是「按下去会得到什么」，不是「现在是
什么」。** 于是按钮的脸就是那个结果的图，`faces` 一张表就够，一行判断都不用写。**下次遇到
「三态循环」的游戏，先看标签说的是结果还是状态**，是结果就照抄这七个。

**pattern 是这七个之外的那一个，而它不在里面的理由不是技术上的。** 它的标签同样说的是结果，照
抄这七个就能跑（第三步就是这么做的）。不照抄，是因为「脸跟着标签走」在它身上会让按钮的位置失
去含义。`does` 就是为这一步存在的：**按钮的名字是那个结果，由标签反查此刻哪个键能给出它**，于
是三个位置各自钉死一个颜色。

**`does` 的第二个使用者是 samegame 的取消选中，而它用的是这个机制的另一半好处。** pattern 要
的是「位置钉死」，samegame 要的是「不重复」：取消选中在四种局面里只有两种能做，一种由 `Space`
提供、另一种由 `Enter` 提供，而按键盘照抄会让这个按钮在其余两种局面里变成 `Enter` 的复制品。
按结果命名之后它自己知道什么时候该灭。

### samegame 的取消选中，以及一条被用错过的判据

上游 `current_key_label`（samegame.c:1098）四行，只有「已选中」那行两个键不同：`Enter` 是
`Remove`、`Space` 是 `Unselect`，`interpret_move`（1302）里对应 `sel_movedesc` 和 `sel_clear`。
我们一开始只给了一个键，把 `Unselect` 判成「不同但没用」，理由是：换选区不需要先取消（未选中格
那一支是 `sel_clear` 之后才 `sel_expand`，1307 行上游自己注释着 "might be no-op"），而且长按棋
盘就能取消（长按默认是右键，上游那行写的是 `RIGHT_BUTTON || CURSOR_SELECT2`）。**这两条事实都
是真的，实测都成立**：取消之后状态栏从 `Selected: 4 (4)` 回到 `Score: 0`，走子数不变。

**错的是判据，不是事实。**「触摸有别的路够得着，所以不给按钮」在这个仓库里从来没被执行过——
mines 的插旗同样在 `Space` 上、同样长按也能做，照样给了按钮。真正在执行的那条线是 **netslide
那条：上游的键盘上有没有**。netslide 的反向推只在右键上，所以不给；samegame 的取消选中在
`CURSOR_SELECT2` 上，所以要给。

补上之后顺带堵了一个我们自己开的洞：**孤立格上上游的 `Enter` 会清掉选区，而我们的单个按钮在那
里是灰的**——比它自己发的那个键少做一件事。选着一块区走一遍棋盘，144 次停靠里 47 次是这一格。
现在那一格左键仍然灰着（没东西可选，这句是真的），右键亮着（有东西可取消）。

## 按钮有两层，而这一行是当前那一层的菜单

有些谜题不是一按就落子，而是两步：**第一步挑出一件东西让它待定**（棋盘上高亮、状态栏开始说
话），**第二步处置它**——确认或放弃。这一行按钮是「当前这一层的菜单」，不是「这个谜题所有按钮
的固定清单」。

**rect 是这个模型最容易被看漏的例子。** 它一级是「画矩形 / 清内部」，二级是「完成 / 取消」，
两级各两项，同一对按钮换脸——正因为数量相等，看起来像什么都没发生，其实整套菜单已经换过一次
了。samegame 一级一项、二级两项，换的时候长度跟着变。**两者是同一件事，rect 那次只是被数量掩
盖了。**

于是「按不动」分成两句不同的话，而且都需要：

| 画法 | 说的是 | 例子 |
| --- | --- | --- |
| **不在菜单里** | 这件事在这一层不存在 | samegame 一级的「取消」——还没选中任何东西，取消没有宾语 |
| **置灰** | 在这一层里，但此刻做不了 | samegame 站在孤立格上的「选中」；rect 二级里还没拖动的那个灰勾 |
| 照常亮着、按下去无事 | 在这一层里，而且已经是那个样子（幂等） | pattern 的三个颜色键（`lit`），全 app 唯一 |

第二行那个灰勾当初是按「第一个按钮的语义永远是 done」加的，现在回头看，它就是这条规则的一个
实例，只是那时候还没有名字。

### 怎么写下来的

**声明，不是附带。** 同样的效果本来可以白捡：`does: 'Unselect'` 在没有选区时找不到人提供那个
词，本来就会返回 null。但那样规则就藏在 `does` 的行为里，下一个不用 `does` 的二级按钮没有依据
可循。所以是两件明写的东西：

- `CursorKey.level`——这个格位只在第二层出现（现在只有 samegame 的取消键有）。
- `SECOND`——每个谜题声明**哪些词表示第二层开着**。samegame 只有一个词：`['Remove']`。

### 只有一个词，而这是这一节最贵的一课

`Remove` 只可能从 `if (ISSEL(ui->xsel, ui->ysel))` 那一支出来（samegame.c:1104），没有第二条
路能产生它。所以**「报出 `Remove`」和「光标正站在选区上」是同一件事的两种读法，双向成立**，层
级因此是纯函数,一个字节都不用记。

第一版把 `Unselect` 也放了进去，于是需要一个自留的 bit、一个 ref、一条「只有方向键能让它活过
去」的规则，还踩了一个 React updater 延迟读 ref 的坑。全部都是多余的，而多余的根源是一句话读
错了：

> **我把第二层理解成「有一个待定物存在」——那是关于整块棋盘的事实，标签确实说不出来。**
> 但菜单是关于**光标站在哪儿**的：它的两项是「确认**这个**」和「取消**这个**」，那个东西得在手
> 边，两句话才有意义。这么读，层级就是位置的函数，而位置正是 `current_key_label` 在描述的东西。

`Unselect` 之所以毒，是因为它有两个来源——选区上的 `Space`，和孤立格上的**两个**键（那一支由
`ui->nselected` 守着）。把它算进来，等于把「读者已经走开了」也算成第二层，而走回去的那一刻标签
又说不清楚，于是只好记。

**光标睡着时也不显示,而这是一处漏掉之后才补的。** 棋盘按压会把光标收起来（samegame.c:1285），
但标签仍然描述着光标**离开前**那一格；如果那一点恰好选中了包含那一格的区域，`Remove` 就会照常
上报,取消键于是出现在一块没有光标的棋盘上。`faceOf` 早就不信睡着时的标签了（第一个键会退回静息
脸），`inMenu` 却还信——**同一份数据两种信任度,这就是那个 bug**。现在 `inMenu` 先看 `awake`，
再读标签:第二层的意思是「读者正站在那个东西上」，棋盘上没有光标时没人站在任何地方。

**孤立格上不显示取消，是对的。** 上游在那里确实答 `Unselect`，但那个清除是 `else` 分支里
`sel_clear` 之后 `sel_expand` 没找到东西的**副产物**，不是一件被设计出来的动作；上游给它一个词
是照实描述后果。同理，「站在另一块可选区上取消键消失」也不是缺陷——那儿本来就是第一层。这两条
我都先判错过一次，判错的方式一样：拿「上游那个键按下去会发生什么」当成了「这一层有什么」。

**`CURSOR_KEYS` 因此从「一排按钮」变成「一排格位」。** `data-act` 取自**未过滤**的下标，所以
一直在的那个按钮永远不动位置——实测 samegame 的左键在一级、二级、回到一级时都在 x197，右键来
去不影响它。否则哪天二级键排在前面，一级键会在进二级时横向挪一格。

**认不出标签时全部显示。** `inMenu` 在 `understood()` 为假时一律返回 true：上游改个词的代价应
该是一个「亮着但按不动」的按钮，而不是一个消失了、且没有任何办法把它要回来的按钮。和这个文件
里其它几处的取舍是同一笔。

**范围只到 samegame。** 按词表看，另外八个谜题也有第二层——pegs、bridges、signpost、pearl、
galaxies、map、filling，加上不需要声明的 rect。它们各自轮到时再加自己那一行；现在一次写完等于
对八个没量过的谜题下八个断言。

## 我们自己保存的状态

**默认是零。** 这一侧的东西全是推导出来的，不是记下来的：`keysFor` 读 game id，`wouldSend`
读后端报的标签，`marks` 把存档 replay 一遍。推导不会漂，副本会。所以这一节是一张**要保持
几乎空着**的表，加一条之前先读完下面那三行判据。

**四十个做完之后的最终结果：三十九个游戏，六个需要副本。** net、samegame、flip、guess、
dominosa、flood 各需要一个 boolean——代码里是同一个 `awake`，因为同时只挂着一个谜题。其余
三十三个一个字节都不记。这个比例是这一节存在的意义。

**为什么恰好是这六个，是数出来的，不是挑出来的。** 四十个游戏的 `current_key_label` 逐个读了
一遍，分成三堆：

| | 个数 | 要不要副本 |
| --- | --- | --- |
| 函数是 `NULL` | 5（cube、fifteen、loopy、untangle、palisade） | 不要——前三个不读这两个键，后两个走 `SILENT` 豁免 |
| 实现了，而且开头检查自己的可见性标志 | 28 | 不要——「两个词都空」本身就等于「没光标」 |
| 实现了，但不检查 | 7 | 6 个要，inertia 不要 |

第三堆的 7 个是 net、samegame、flip、guess、dominosa、flood、inertia。**inertia 掉出去是因为
它根本没有光标**——`game_ui` 里五个字段没一个是坐标，它的 `Advance` 读的是 `state->soln`。所以
剩下六个，这个数字没有可调的余地。

分类靠的是读，不是 grep：可见性标志有十种拼法（`cur_visible`、`hshow`、`cshow`、`cursor_show`、
`cursor_active`、`cursor_visible`、`cdisp`、`cursor`、`cdraw`、`displaysel`），检查的位置也各在
各的地方。

| 名字 | 存什么 | 谁写 | 影响哪些游戏 |
| --- | --- | --- | --- |
| `labels`（PuzzleHost） | 两个字符串 | **后端**，`onKeyLabels`，每次输入后整对覆盖 | 37 个有肩键的（除 untangle、palisade 两个不报的） |
| `awake`（PuzzleHost） | 一个 boolean | **我们**，见下 | net、samegame、flip、guess、dominosa、flood |
| `opened`（PuzzleHost） | 一个键名 | **我们**开拖拽时写，**后端**一有能力就改写 | rect 一个（见「三件跨游戏的事」里 Rectangles 那段） |

`labels` 不算副本——它是镜子，唯一的写入者是后端，我们一个字都不推导。另外两个才是这一节真正
说的东西：「后端知道但不肯说，于是我们自己记着」。

**这里短暂地有过第三个，`picked`，而它被删掉的过程值得留下来。** 它是为「samegame 的取消键该
不该在」加的，加完能跑、测得过、文档也写了——然后发现整件事的前提读错了：第二层不是「有一个待
定物」而是「光标站在待定物上」，换成后一种读法，`SECOND` 里少一个词就够，状态整份消失。**「需
要记一份状态」这个结论本身，应该先被当成一个可疑信号**，而不是一道要去解的题。

### 加一条之前

三条，缺一条就别加：

1. **上游确实没有接口。** 不是「不好拿」，是拿不到。`awake` 满足：`midend_get_cursor_location`
   存在但 emcc.c 既不调用也不导出；存档里没有（只有 5 个游戏写 `encode_ui`，net 写的是
   org 和 centre，不是光标）；标签里也没有，因为 net 的 `current_key_label` 根本不问。
2. **输入面是封闭的。** 送进 `interpret_move` 的每一样东西都得经过这一侧，否则副本必然漂。
   现在成立：`PuzzleHost` 的 `onKeyDown` 转发每一次按键，`usePuzzlePointer` 转发每一次棋盘
   触摸，方向键和肩键走 `sendKey`。
3. **失效是自纠正的。** 猜错要能在一两步内自己回到正轨。`awake` 猜成「灭」而实际是亮的，
   结果是按钮多灰一下，下一次方向键两边就同步了；猜成「亮」而实际是灭的，就是没做这件事
   之前的行为。两种都不粘。**这条是 `marks/` 过不了的那条**——那边猜错会擦掉玩家写的候选，
   所以那边的规矩是「读不懂就整个拒绝」，不是「记一份」。

### net 的 `awake`

第一个，也是上面那张普查表里第三堆的头一个：net 的 `current_key_label` 不检查可见性标志——它
无条件读 `tile(state, ui->cur_x, ui->cur_y)`
（net.c:2124），所以刚发牌、光标还没出现时它就报 `{Lock, Rotate}`，说的是中间那格
（`new_ui` 把光标放在 `width/2, height/2`，net.c:2043）。而 net 的 select 键是**一边转一边
才把光标显出来**（net.c:2330），不像 pattern 的先显出来就返回。按钮亮着、按下去转了一块你
根本没看见被选中的 tile——这就是要修的。

四条规则，都是从 C 里读出来的：

| 什么时候 | 灭/亮 | 依据 |
| --- | --- | --- |
| 开局 | 灭 | `new_ui` 读 `PUZZLES_SHOW_CURSOR`，wasm 里没有（net.c:2045） |
| 碰棋盘 | 灭 | net.c:2172，而且在越界检查**之前**，所以点在格子外面也算 |
| 后端重建 `game_ui` | 灭 | `midend_new_game`（midend.c:659）、`midend_deserialise`（midend.c:2623） |
| 按下唤醒键 | 亮 | 方向键走 `MOVE_CURSOR`（net.c:2415），`Enter`/`Space`/`a s d f` 走 select 分支（net.c:2330） |

两条值得单独记：

- **Shift/Ctrl + 方向键不唤醒。** 它们在 net 里是 `MOVE_ORIGIN` / `MOVE_SOURCE`，移的是别的
  东西，不碰那个标志。所以 `onKeyDown` 里要看修饰键。
- **重新开始不灭。** `midend_restart_game` 保留 `me->ui`，只调 `changed_state`
  （midend.c:939），而 net 的 `changed_state` 是空的。这条是查出来的，不是想当然——按直觉写
  会多一条错的规则。

第三条规则**没有**写成一串调用点，而是接在后端自己的通知上：`game_id_change_notify` 只从
`midend_new_game`（midend.c:664）和 `midend_deserialise`（midend.c:2722）发出，正好就是那两处
`new_ui` 所在的函数，各差五行。它一路走到 `js_update_permalinks`，也就是 `onPermalinks`。所以
新游戏、换预设、手打 game id、手打种子、恢复存档、标记键的 `loadGame`——**六条路一行覆盖**，
以后多出第七条也照样覆盖。`midend_supersede_game_desc` 也发这个通知而不重建 ui（mines 的第一
次点击），两头都无害：那一下本来就是碰棋盘，而且 mines 这边没有副本。

### samegame 的 `awake`

第二个，理由和 net 一模一样：它的 `current_key_label` 读 `ui->xsel, ui->ysel` 而从不问光标
在不在屏幕上（samegame.c:1098），所以新开的盘上它已经在报左上角那个区域能做什么；而它的
select 键是**立刻动手**而不是先显光标——`ui->displaysel = true` 然后直接进选择逻辑
（samegame.c:1291）——于是盲按会选中一个谁都没指过的区域。

规则比 net 少两条（没有 `a s d f`）：开局灭、碰棋盘灭（samegame.c:1285）、`new_ui` 重建灭、
方向键或 `Enter`/`Space` 亮。方向键是 `wrap = true`，光标在网格上绕圈，没有边框问题。

**它的标志叫 `displaysel`**，这就是为什么全集扫描会漏掉它。十个游戏十种拼法：`cur_visible`、
`hshow`、`cshow`、`cursor_show`、`cursor_active`、`cursor_visible`、`cdisp`、`cursor`、
`cdraw`、`displaysel`。**没有别的办法，只能一个一个读 `game_ui`。**

### flip 的 `awake`

第三个，而且理由比前两个更硬：net 和 samegame 至少还在说一件关于某个格子的真话，flip 的
`current_key_label` 整个函数是

```c
if (IS_CURSOR_SELECT(button)) return "Flip";
return "";
```

（flip.c:934）——**一个常量**。光标亮着、灭着、棋盘解完了，它都说 "Flip"。所以标签在这里一个
字节的信息都没有，副本是「按下去」和「盲翻左上角那一格」之间唯一的东西。

它的标志叫 `cdraw`，规则是 samegame 那四条，外加一个小差别：**只有 `LEFT_BUTTON` 会清掉它**
（flip.c:959），因为 flip 根本不读别的按钮。于是长按会让这一侧睡下而上游那边光标还亮着——
**朝安全方向多睡了一下**，下一次方向键就同步（而且 flip 里长按本来就什么都不做）。

### guess 的 `awake`

第四个，理由和前三个同一条（标签不问 `ui->display_cur`，而 select 键按下就放子，guess.c:933），
但它的唤醒键表是目前最长的一份：guess 读的键最多，而且几乎每一个都会显示光标——数字键插入
颜色（guess.c:943）、`D`/`Backspace` 清掉一枚（952）、`h` 跑提示器，而提示器会顺手把光标显出来
（那是 guess.c:799 那段「用一点 ui 变化表示算不出来」的 hack 的副作用）。

**`h` 那条对我们是实打实的，不只是键盘。** 它在 guess 的键盘上有按钮，拇指够得到——所以
`pressKey` 现在也问一次 `wakesCursor`。**这是键盘区和十字区唯一一处重叠**，四十个游戏里只有
guess 撞上：net 的 `J` 不显光标，samegame 和 flip 没有键盘。

### guess 的颜色键：判据说不给，还是给了

键盘上有 `ncolours` 个颜色键（`c6p4g10Bm` 里的 `c6`）加一个 `⌫`，每个画成它按下去要放的那枚
棋子——颜色取自棋盘此刻正在用的调色板，读者要是开了「Label colours with numbers」，键上还会
跟着出现数字，跟棋盘一模一样。这是这份文档里**唯一一处明知不满足判据还是做了的**，所以两边
的账都记在这。

**判据说不给，三条都说。**

- **放一枚颜色够得着**：从左边那条颜色柱**拖**到棋子位上（guess.c:857-859、888-892）。实测
  触摸下成立：390×844 和 320×568 两档都能放进去，颜色柱上每一格分别是 45 和 27 CSS px。
- **删一枚也够得着**：捏住已经放好的那枚**拖出这一行**再松手（`drag_opeg > -1` 走
  `set_peg(..., 0)`，guess.c:895-899）。两档都实测过。而且拖拽还多干一件键盘干不了的事：从
  **上面某一行旧猜测**里拖一枚颜色下来（guess.c:872-878）。
- **第二条也不成立**：方向键把光标移到棋子位上之后本来就有东西可按——上下键移的是
  `ui->colour_cur`，棋盘会在选中的那枚颜色上画一个光标圈（guess.c:1420-1426），`Enter` 放的
  就是它。光标不靠颜色键才有意义。

（这三条最初是写成「所以不给」的。前两条纠正的是更早一版的记错——那时写着「数字键还差，是
一件独立的活」，而错法是「看见一个键映射到某个动作，就当那个动作只有它能做」，和 mines 的连开
同一个错，见「已经踩过的坑」。**两次都是只读了 `interpret_move` 里键盘那半边。**）

**给的理由只有一条，而且不在判据里：够得着的那条路是一次拖拽。** 这一整套四十个谜题，别的地方
没有一处要求读者按住再拖；guess 的这条是唯一的例外，而且它还是**唯一的**入口。判据问的是「够
不着吗」，答的是「够得着，只是得拖」——这两句话都对。

### 颜色键会先把棋盘上那个圈瞄准自己，而这不需要读出它在哪

上游的颜色键写完格子会把 `peg_cur` 往前推一格，却从不动 `colour_cur`（guess.c:940-947）。于是
按 `3` 落下绿色、再按 `Enter`，第 1 位落下的是**红色**——`Enter` 放的是圈指着的那个，圈没跟着
走。键盘上无所谓（`3` 是你自己敲的），但屏幕上多了一排彩色按钮之后，就有两个东西同时在回答
「现在选的是哪个颜色」而答案不一样。

这条曾经记在「遗留问题」里，理由是「要让圈跟着走就得知道圈在哪，而位置读不到」。**前半句是错
的：不需要知道它在哪。** `move_cursor` 在 `wrap = false` 时是**夹住**而不是绕回
（misc.c:378），而 guess 传的正是 `false`（guess.c:928）。所以连按 `ncolours` 次「上」，无论
原来在哪都会停在第一个颜色，再按 `i` 次「下」就落到第 `i` 个。**推导，不是记忆**——和 cube 的
置灰箭头同一类。

（`encode_ui` 确实不存光标，只存当前这一行的棋子和 hold，guess.c:467。所以「读不到」那半句
成立，错的是「因此做不到」。这也是这个仓库里第二次把「读不到」当成「办不到」——第一次是
netslide 的方向。）

实测(`UI` 那一行就是当前这一行的棋子，存档里读得到)：

```
按颜色 3            UI: 3,0,0,0     走子 0
再按 Enter          UI: 3,3,0,0     ← 从前这里是 3,1,0,0
按颜色 6 再 Enter   UI: 3,6,6,0
新局，敲 1 4 2 5    UI: 1,4,2,5     ← 数字键该有的前进一格没丢
```

**代价量过，三条都小：** 不进撤销历史（`move_cursor` 回的是 `MOVE_UI_UPDATE`，midend 只重画不
压栈，走子数全程 0）；不闪（所有按键在一个点击处理里同步跑完，浏览器只合成一帧，六个颜色实测
1.7–6.1 ms）；不动 `peg_cur`（上下只走 y）。走的次数是 `span + at`，从近的那一端数起，最多
1.5 × `ncolours`。

**失败模式是安全的。** 万一上游哪天把 `wrap` 改成 `true`，走完会落在任意位置——但棋子仍然是对
的，因为落子是那个数字键干的。这条回归退化成的正是本节开头那个毛病，不会退化成放错颜色。

**这让我们的颜色键不再逐字等于上游的数字键**，而这是有意越的一条线：上游读者自己敲了 `3`，心里
知道；那排彩色按钮是我们摆上去的，两个「当前颜色」也是我们造出来的，所以由我们收拾。

### 后来的收尾：把这一条破例交给读者

上面那笔账两边都成立——键盘上有的东西给了按钮，而它并不满足判据——所以最后没有由我们替读者
判。**颜色键和 `⌫` 现在是 guess 偏好设置里的一个开关，默认关**（`puzzles.keys`，`useKeys`，
和方向键完全同形：一组游戏名存一个 key，presence 即真）。想省一次拖拽的人自己打开，不需要的人
拿回那一行的高度。

**开关只给 guess，而这是一个逐个游戏读出来的判断，不是一条规则。** 关掉的是 `whose` 为空的那些
键——「往格子里放东西」的那一档——而这一档在别的谜题里恰恰是唯一的入口：手机上没有任何办法往
solo 里敲一个数字、往 undead 里放一只怪物。把开关铺开等于给读者一把能锁死自己的钥匙。名单
（`offersKeys`）现在只有 guess 一个名字，每加一个都得先读那个游戏的鼠标处理。

**`H` 不跟着关，这是那条线。** 它是 `whose: 'upstream'`，而 `compute_hint` 只挂在 `'h'`、`'H'`、
`'?'` 上（guess.c:929），**没有任何鼠标路径**。关掉它就是把那一排上唯一一件触摸设备原本做不到的
事收回去——而那正是这一排存在的全部理由。所以开关关着时那一行仍在，只剩一个键；net、fifteen、
bridges 本来就是这个样子。

**`l` 不给按钮。** 它是一条真的偏好设置（`PREF_SHOW_LABELS`，guess.c:442），早就在偏好设置弹窗
里了，那一栏写的就是「Label colours with numbers」。它在这里的作用是决定颜色键上有没有数字，
所以 guess 进了 `READS_PREFS`——和 undead 同一个理由，按完键回去重读一次。

### `⌫` 是向后删的，而这需要后端回一句话

上游的 `\b` 清的是**光标所在**的那一格（guess.c:948），而颜色键放完子会把光标往前推一格
（946）。两条合起来的后果是：刚打完四枚棋子想把最后一枚撤掉，按 `⌫` 什么都不会发生——得先按
一次左。一排彩色键上面画着 `⌫`，那就是在打字，而打字的地方退格从来不是这个意思。

所以这个键**发两下**（`KeyLabel.behind`，`PuzzleHost` 里执行）：先在原地按一下，如果那一下白按
了，就往左走一格再按一下。**先试原地**不是多余的：光标停在一枚棋子上时，读者要的就是这一枚，
而上游的语义在那种情况下本来就对。两种读法只在空格子上分道扬镳，而空格子上上游那条什么都不做。

**最多两下。** 「一直退到删掉点什么为止」会在一次本该无事发生的按键上把整行走穿。

判断「那一下白按了」靠的是**后端回的唯一一句不是标签的话**：`key()` 在「这个键认识、但没产生
任何效果」时返回 false——而且只对**一个**键这么做，就是拼作 `Backspace` 的那个
（emcc.c:456，本来是给 KaiOS 的一个照顾）。所以这个键按名字发而不是按字符发；midend 反正会把
8、127 和 `\b` 折成同一个 button（midend.c:1261）。实测：光标显示着、格子是空的 → false，
格子有棋子 → true，光标没显示 → true（那一下会把光标点亮）。

**`notAt` 那一格是防越界的。** 光标走过最后一枚棋子时标签读作 `Submit`，而上游的清除分支是
那个函数里**唯一一条没有先检查 `peg_cur` 边界**的（数字键检查了、`CURSOR_SELECT2` 检查了、
`CURSOR_SELECT` 分支了），在那里按下去会读、并且可能写到整行之外一个 int。所以在 `Submit` 上
先走一格再按，落点是最后一枚棋子——反正也正是读者要的那一枚。

**物理键盘没改，是有意的。** 键盘上的 `Backspace`（和 `d`/`D`）仍然是上游的意思：清光标所在的
那一格。这一侧加的按钮可以有自己的语义，上游的键不该被改写意思——`index.css` 里那条「上游键的
文案和顺序以上游手册为准」是同一件事。手册对这个键的说法是「\q{D} or Backspace removes a
peg」，没说哪一枚。

### dominosa 的 `awake`

第五个，理由和前四个同一条，但它的唤醒键表是最短的一份：**只有方向键**。
`move_cursor` 拿到了 `&ui->cur_visible`（dominosa.c:2831），而那个函数里再没有别的地方写它
——select 键放骨牌/画线时不写，数字键只点亮数字也不写。所以键盘上按一个 `Enter`、光标是灭的，
上游会在没人看得见的地方落一张骨牌；棋盘也不画光标，我们的按钮也照样灰着，两边是一致的。

清除照旧是「碰棋盘」，但上游只在**产生走子的那条路**上写 `cur_visible = false`（2823）。在数字
上右键只翻高亮，早在那一行之前就返回了，于是上游留着光标而我们收了起来——过度睡眠，安全的那
个方向，和 flip 同一笔交易，下一次方向键就纠正回来。

### flood 的 `awake`，以及它教会的一件事：副本盖住的是**键**，不是游戏

第六个，理由和前五个同一条：`current_key_label` 只问光标底下那格颜色和左上角一不一样
（flood.c:830），从不问光标在不在，所以光标收着的时候它照样提议从上一次停的地方淹一片。唤醒
键表和 dominosa 一样只有方向键。

**但它的第二个键不该被这份副本盖住，而一开始被盖住了。** `Space` 是 `Advance`——重放求解器的
下一步，走的是 `state->soln`，`ui->cx, ui->cy` 一个都不读（flood.c:855）。上游自己就是这个态度：
按下求解那一刻标签立刻变成 "Advance"，中间不需要任何方向键。而我们的门是按游戏名关的
（`mirrorsCursor(name) && !awake`），于是**按了求解之后那个按钮是死的，直到你按一下对它毫无
用处的方向键**。

实测，改之前：

```
fresh board            Fill [disabled]  Advance [disabled]
after solve, no arrow  Fill [disabled]  Advance [disabled]   ← 应该是活的
after one arrow        Fill [live]      Advance [live]
```

**它看不出来，这才是这条值得单独写的原因。** 置灰的按钮仍然戴着自己那张静息脸，而 `Advance`
的静息脸和它工作时的脸是同一张，所以屏幕上「死的」和「活的」长得一模一样——只有
`disabled` 属性知道，也就是只有测试知道。这和之前踩过的「测试读标签而不读 `disabled`」是同一个
坑的两面。

修法是把门从游戏挪到键上：`CursorKey.offCursor` 标记「这个键不在光标那儿干活」，`wouldSend`
和 `faceOf` 都改问 `gated(name, cursor)`。全集里只有这一个键带这个标记——其余十一个肩键都是在
光标所在的格子上动手，问的正是这份副本答的那个问题。

改之后：`after solve, no arrow` 那行的 `Advance` 变成 live，`Fill` 仍然 disabled（对的，光标确实
没显示），六个游戏的「灭 → 一次方向键 → 亮」全部照旧。

### 后端一个字都不报的两个

**两个都做完了。** untangle 和 palisade 的 `current_key_label` 是 `NULL`，所以
`midend_current_key_label` 对两个键永远回空串。**照字面读就是「两个键都没用」，两个按钮会
整局灰着**——这是这份文档里第一次出现「没有传感器」的情况，前面二十个游戏的置灰全靠那两个词。

办法是**豁免，不是伪造**：`keys.ts` 的 `SILENT` 列出这两个游戏，`wouldSend` 见到就直接返回
按键、不去问标签。代价是按钮永远可按，而这在 untangle 上几乎是真的：

- `Enter` 的三条分支**每一条都做事**——没有高亮点时把第一个点亮出来，有高亮点时拿起它，
  拿着时放下（untangle.c:2395-2437）。**不存在「按下去看不见任何变化」的状态**，所以也
  不需要副本。这是目前唯一一个既没有标签、也不用记任何东西的游戏。
- `Space` 只在「点正拿在手上」时是空按（2445 直接 `MOVE_NO_EFFECT`）。一次空按换掉一份
  副本，值得——而且棋盘正把那个点画成另一种颜色，读者看得见自己在拿着东西。

**palisade 的代价比 untangle 大，而且大得可以量。** 它的光标走半格网格：偶数位是格子中心和
角，奇数位才是两格之间那条边，而只有边上按下去才有事发生（palisade.c:1092 的 `px == py` 直接
返回 `MOVE_NO_EFFECT`）。dominosa 是同一个形状，但它会报标签，所以在没用的落点上两个按钮会
灭掉；palisade 不报，于是**一半的按键是空按**——实测走 26 步按 26 次，13 次什么都没发生。
没有修：要修就得自己记住光标的奇偶，而点棋盘会把光标扔到任意位置，那份副本立刻就漂了，正是
上面三条判据里「失败能自愈」那条不成立的样子。

**palisade 还是唯一一个「偏好设置决定按钮存不存在」的游戏。** 它的光标有两种模式：Half-grid
（走边，`Enter`/`Space` 画墙）和 Full-grid（走格子，画墙要按住 Ctrl/Shift 再按方向键）。修饰键
我们发不出去，而它又不报标签，所以在 Full-grid 下这两个按钮会一直亮着且永远无效——**宁可不
给**。`cursorKeys(name, prefs)` 因此多了一个参数，palisade 也进了 `READS_PREFS`。上游默认是
Half-grid，所以正常读者拿得到这两个键。

**这个游戏的方向键和别处都不一样，值得单记一笔。** 它不是走格子，是**按象限找最近的点**
（untangle.c:2287-2350）；而一旦有点被拿起来，同样四个键改成每次推半格。所以 `Enter` 不只是
「让方向键有意义」，它是**换掉方向键是什么**。`Space` 因此也不是同义词：象限搜索会跳过和当前
点完全重合的点（2313），上游自己给的出路就是这个键。

### 那份「其余 7 个候选」的名单是错的

这里曾经列着「`current_key_label` 不检查可见性的还有 7 个：inertia、tents、range、pearl、
unruly、flood、tracks」。**逐个读过之后只剩一个**：tents 查 `cdisp`、range 查 `cursor_show`、
pearl 查 `cursor_active`、unruly 查 `cursor`、tracks 查 `cursor_active`，全都自己把关了；
inertia 根本没有光标。**只有 flood 是真的不查**——它的标签只问「光标底下那格和左上角是不是
同色」，别的什么都不问（flood.c:830），所以它是第六个、也是最后一个需要副本的。

那份名单是怎么来的：当时 grep 的是 `cur_visible` 这一个名字，而这些游戏各叫各的
（`cdisp`、`cshow`、`cursor`、`cursor_show`、`cursor_active`）。**要判断一个游戏查不查，
只能把那个函数读一遍**，名字数不出来。共通的只有形状：每个有光标的游戏在 `game_ui` 里都有一个
bool，方向键会点亮它（多数经由 `move_cursor` 的最后一个参数，misc.c:365 在里面写
`*visible = true`），碰棋盘会灭掉它。inertia 例外，它根本没有光标——棋盘上那个位置就是它自己。

顺带：**有副本的游戏，按钮在「不知道光标在哪」时戴的是自己的默认脸**，不是标签当下说的那张
（`faceOf` 里那个 `awake` 判断）。否则 samegame 会在两个灰按钮上显示左上角那个区域的状态，
而光标根本不在那儿。

而且第一步永远是：**先确认这个游戏真的需要副本**。三十三个不需要，普查表在这一节开头。

反面的例子就在「已经踩过的坑」那节：Sixteen 把光标挡在棋盘内，看起来很像需要记住光标在哪，
实际上一个字节都不用——发完键看一眼标签，在边框上就退回去。**能用「问一句」解决的，不要用
「记一份」解决**，哪怕问的那一句要绕一点。

## 已经踩过的坑

**别只读按键处理函数就下结论——Cube 教训。** Cube 读 numpad 7/9/1/3，手册也写着
「can be used for diagonal movement」，看起来和 Inertia 一样是八向。但方向是**每个格子自己
声明**的：正方形网格四个斜向全是 `0`（`cube.c:350-353`，注释就写着 "no diagonals in a
square"），三角网格上它们是别名（`UP_LEFT` 接 `LEFT`，两个下斜向都接 `DOWN`，
`cube.c:408-411`、`453-456`）——一个三角形有三个出口，不是八个。实测四个预设十六个位置，
没有一次斜向能到而箭头到不了。**Inertia 是真八向**（`inertia.c:41-42` 的 `DX`/`DY` 展开是
八个不同位移）。

**死代码看起来像功能。** `tracks` 的 `h` 包在 `#if 0` 里，`signpost` 的 `h` 整段被注释掉了。
两个都不要照着加。

**`current_key_label` 现在接上了。** 35 个游戏实现了它，按当前光标位置返回一个活的词：Net 在
锁着的格子上说 `Unlock`、没锁的说 `Rotate`/`Lock`。这条链路一路通到
`PuzzleCallbacks.onKeyLabels`，以前在 `PuzzleHost` 里撞上 `onKeyLabels: () => {}`，现在存进
state，`keys.ts` 的 `wouldSend` 拿它决定一个光标键该发哪个键、还是干脆置灰。

这也是这一侧唯一能知道的关于光标的事：`midend_get_cursor_location` 存在，但 emcc.c 既不调用
也不导出，位置够不着。**两个词就够了**，因为要问的只是「现在按下去有没有用」。

**后端还回一句话，只有一句，而且只对一个键。** 标签是按之前问的，`key()` 的返回值是按之后
答的：它在「这个键认识、但没产生任何效果」（`PKR_NO_EFFECT`）时返回 false——**仅限拼作
`Backspace` 的那个键**，emcc.c:456，本来是给 KaiOS 的一个照顾，别的键一律返回「认识」。
guess 的 `⌫` 就是靠它才敢向后删（见「`⌫` 是向后删的」）。要用它先看清楚这条窄：换一个键、
或者上游哪天把那个 KaiOS 分支删掉，这个传感器就没了，而它没了的时候什么都不会报错。

有一条不对称，是被逼出来的而不是选的：`js_update_key_labels` 在 `lsk === csk` 时把 `lsk` 抹成
空串。实测 Solo 和 Unequal 在同一种局面下都报 `{"", "Pencil"}`——Solo 的 `Space` 是真死
（`current_key_label` 只答 `CURSOR_SELECT`），Unequal 的 `Space` 和 `Enter` 干同一件事
（`IS_CURSOR_SELECT` 两个都盖）。**从这一侧分不出来**，所以 `Space` 只在两个词都空时才算死。
按一下白按是小事，一个永远灰着的按钮是没人找得到的功能。

置灰说的是「对棋盘没用」。有两个游戏，标签空着时按下去仍然会**唤醒光标**——Pattern 的
select 会先把光标显出来就返回（`pattern.c:1423`），Net 的会在去做一次锁定挡下的旋转的路上把
`cur_visible` 设成 true（`net.c:2330`）。它们照样置灰：方向键就在同一组里，一样唤醒光标，而且
还会说光标去了哪。

**光标能走出棋盘的只有 Sixteen，而我们曾经把它挡回来——那段代码已经删了。** 它的光标在一个比
棋盘宽两格高两格的网格上走（sixteen.c:657-686），所以方向键会把它带进四周那圈推行箭头，四个角
还会把它弹到相邻的边上。曾经的做法是**踩出去再退回来**：发完方向键看标签，报 `Slide`/`Back`
就补一个反方向键，同一个 JS task 内完成，浏览器只画一次。机制本身是好用的——实测 50 次来回，
光标回原位，走子列表一条不多（方向键返回 `MOVE_UI_UPDATE`，midend 不记成状态）。

**删掉的理由不是它不好使，是它在解决一个不该解决的问题**：把光标赶出上游给它的一半地盘，好让
按钮少两张脸。判据第三条那节写了为什么这笔账反了。现在四张脸都在，光标想去哪去哪。

留一条从那次实现里学到的、和 sixteen 无关的东西：**要读 ref，不能读 React state。**
`post_move` 是同步的（emcc.c 里 `midend_process_key` 下一行就是它），所以 `api.key()` 一返回
标签就已经更新了，但 React 还没渲染——实测那一刻按钮的 `disabled` 还是旧的。`onKeyLabels`
因此同时写一个 ref 和一份 state；guess 的 `⌫` 现在还在用那个 ref（`notAt`）。**它仍然只有后端
一个写入者，是镜子不是副本**，和「我们自己保存的状态」那节说的 `awake` 不是一回事。

**同一个键在一局里可以换几次工作，而标签会说。** Rectangles 是目前最极端的：`Enter`/`Space`
在空闲时是「画矩形」和「清内部」，一旦开了拖拽，两个键就变成「完成」和「取消」——每个键三个
词，所以按钮的脸不能写死，得跟着标签走（`keys.ts` 的 `faces`）。

**上游给的是五个字符串，不是一张表。** `current_key_label`（rect.c:2374）是十二行的一个函数，
里面只有 `"Mark"`、`"Erase"`、`"Done"`、`"Cancel"` 和 `""` 五个字面量。下面这张表是**照着它的
分支还原出来的**，还原者是我们，所以它可能不全——第一版就漏了一行。**每一对里的顺序也是我们
的排版**，而且和上游相反：`js_update_key_labels` 先传 `CURSOR_SELECT2`，是 `puzzle-lib.js`
把它翻回来，好让这一侧能写 `enter`/`space`。

```
空闲              {Mark, Erase}     两个键各开一种拖拽
拖拽中、还没动过  {Cancel, Cancel}  还没有东西可完成
画中、动过        {Done, Cancel}    开它的那个键完成，另一个放弃
擦中、动过        {Cancel, Done}    反过来
光标没显示        {"", ""}          守卫里的 ui->cur_visible
鼠标拖拽进行中    {"", ""}          守卫里的 !(drag_start_x >= 0 && !cur_dragging)
```

（`{"", ""}` 有**两个**互不相干的成因，第一版把它们并成一行，于是「上游此时不理键盘」这句话
把「光标根本没醒」也算了进去。）

**那两个 `Cancel` 是不是同一件事？是，但不是因为设计如此。** 两个键走的不是同一条路：
`erasing == ui->erasing`（rect.c:2511）只放匹配的那个键进入唯一可能产生走子的分支。进去之后，
因为 `!ui->dragged`，它试的是 `H`/`V`——**翻转单独一条边**——而那要求圆整后的坐标一奇一偶。
键盘光标做不到：`coord_round(cur_x + 0.5, cur_y + 0.5)` 正落在格子中心那一档，返回
`(1 + 2·cur_x, 1 + 2·cur_y)`，**两个都是奇数**（rect.c:2282）。所以两条分支都不触发，而
`reset_ui` 在匹配判断**外面**无条件调用，两边都返回 `MOVE_UI_UPDATE`。

也就是说：**它们相同，是因为键盘的光标站不到边上去。** 同样这几行给鼠标就会分开——点在边中点
上，匹配的那个键会翻转那条边。只是鼠标拖拽期间两个标签都被守卫抹空，按钮根本不参与。

**而这一档我们不画两个 X。** 上游必须给两个，那是**键盘的约束**：两个键要覆盖四个状态，走到
「谁都还完成不了」那一格时，它们没有别的话可说，只能把同一句说两遍。**一对按钮没有这个约束。**

规则是：**开这次拖拽的那个键，从头到尾就是「收尾键」**；另一个从头到尾是「放弃键」。收尾键在
还没拖动时没东西可收，所以**显示一个灰着的打勾**——不是灰着的 X，也不是退回它的静息脸。灰着的
打勾说的是「收尾在这儿，只是现在还收不了」；换成别的图，说的就变成「它现在是另一样东西」了。

**棋盘在这一格什么都不说，所以这两个按钮是独一份的说话人。** `game_redraw` 里画拖拽框的那一行
外面是 `if (ui->dragged)`（rect.c:2775），所以那个框——画中是 `COL_DRAG` 纯红，擦中是
`COL_DRAGERASE` 的 (51,51,255)，rect.c:2660——**要拖动过了才画**。量过：还没动过时棋盘上这两种
颜色各 0 像素；一动，画中的红 543 像素、擦中的蓝 813 像素。也就是说「现在开着一次拖拽，而且是
哪一种」这句话，在那一格里除了这一对按钮没有别人在说。这是灰勾落在**开它的那一侧**、而不是固定
在左边的理由：位置是那一格里唯一还能用来区分两种拖拽的通道。

```
空闲              画矩形 / 清内部
按了「画矩形」    打勾[灰] / X
拖动过了          打勾     / X
按了「清内部」    X / 打勾[灰]
拖动过了          X / 打勾
```

**这要知道拖拽是哪个键开的，所以这里存了一个值**——全 app 第二处自留状态（第一处是 `awake`）。
它值得，而且代价比看上去小：

- **它主要是被推导的，只有一格靠记。** 四个状态里三个标签自己就说清楚了（动过的两个直接点名
  收尾键，空闲那个说没有拖拽）；只有「开了没动」那一格说不出来。`opener()` 每次拿着「上次认为
  的值」进去，返回「标签现在能证明的值」——所以看来的那一格一旦被上游反驳就立刻被改写。
- **猜错是免费的。** 在那一格里两个键**本来就都是放弃**，所以不管猜没猜对，留在亮着的那个按钮
  按下去做的就是它写的那件事。最坏情况是第一次方向键时两个按钮换一次边。
- **输入面是封闭的。** 键盘拖拽只能由我们发出的 `Enter`/`Space` 打开（鼠标拖拽走另一条路，
  而且那时两个标签都被守卫抹空、按钮根本不在场）。
- **关掉的那一侧也是。** Escape 能取消一次拖拽（rect.c:2448），而它不经过任何按钮，是唯一一条
  能让这个值变陈旧的路。它不会：标签退回 `{Mark, Erase}`，`opener()` 里 `enter !== 'Cancel'`
  那行就把它归零。实测「左键开画中 → Escape → 右键开擦中」，灰勾正确落在右边。

**`lsk === csk` 的抹空又咬了一次，这次更隐蔽。** 「开了但没动」时两个键都报 `Cancel`,于是
`lsk` 被抹成空串，收到的是 `{"", "Cancel"}`。照字面读，`Space` 那个按钮会置灰并继续戴着「清
内部」那张脸——告诉读者它会擦东西，而实际按下去是放弃拖拽。修法是读 `Space` 的词时把抹空还
原成 `Enter` 的词（`mine`）。**这条规则每次新加一种「按键盘上的词做决定」的机制都要想一遍**,
`doesNothing` 的不对称是同一件事的第一次。

**然后那个修法本身又是错的，dominosa 上现的形。** 「把空的 `Space` 读成 `Enter` 的词」只有在
抹空**真的发生过**时才对，而抹空只在两个词相同时发生。dominosa 里 `Enter` 在有骨牌的地方报
`Remove`，同一时刻 `Space` 报的是真空串（骨牌旁边不许画线，dominosa.c:2762）——收到的同样是
`{"", "Remove"}`，而两个键**都有** `Remove` 这张脸，于是第二个按钮亮起来，说要擦掉一条根本不
存在的线。

前面四个有 `faces` 的游戏没出事是**碰巧**：它们两个键的词表互不相交，继承来的词配不上任何一张
脸。所以现在多了一张表 `BOTH`——**两个键可能同时报出的词**，也就是抹空唯一可能吃掉的东西。
只有 rect 有一条（`Cancel`）。sixteen 看着像第二条，其实不是：它的 `cur_mode` 是一个三值枚举
（sixteen.c:569），`Unlock` 只会从其中一个键上给出来。

教训写在这里：**「空」和「被抹掉的」分不出来，所以要么有一份「什么可能被抹掉」的清单，要么
就别猜。** 加一个有 `faces` 的游戏时，先把它 `current_key_label` 的所有分支列出来，看两个键能
不能同时给出同一个非空词。

**Netslide 和 Sixteen 的边框光标，四个方向键里只有两个是活的。** 光标沿边框走的是
`c2pos`/`pos2c`/`c2diff` 这套（misc.c:409，专为这两个游戏写的），而 `c2diff` 只给「沿当前这条
边走」的那一对方向返回步长，另一对返回 0——除了四个角上的转弯规则。所以在上边框只有左右能动，
在右边框只有上下能动。

这是上游键盘本来的行为，我们也没法改：标签在整圈上都报同一个词，分不出光标在哪条边，所以
**这两个游戏的方向键不能按这个置灰**。写在这里是因为它看起来像 bug：读者在上边框上按「下」，
什么都不会发生。第一次写 netslide 的用例时就是这么绊了一下——按了十次「右」，光标停在右边框上
再没动过。

**但这不是「方向键从不置灰」，cube 就置灰**，而两者的分界不是「能不能算出来」，见下一条。

### 方向键的置灰只有 cube 一个，分界是「棋盘自己说不说」

先把一个一直挂在注释里的假话拆掉：**「方向键总有地方可去」是假的，而且到处都假**。光标顶到
棋盘边界就按不动，四十个游戏里绝大多数都这样（samegame 的光标绕圈，是少数例外）。我们一直
没管，也不该管——因为**光标画在屏幕上，边界也画在屏幕上**，读者看着就知道这一下按不动。棋盘
已经把话说了，我们不必再说一遍。

**cube 是唯一一个自己把答案盖住的。** 三个三角多面体上，能不能往上/往下滚取决于脚下那一格
三角朝哪边——而多面体画得比一格还大，正好压在那一格上。读者要么从周围的贴砖推，要么按一下
试试。实测三角网格上 **33%~42% 的方向键按下去是空的**，其中形状造成的那部分（13/16、24/28、
54/60）完全不可见。

所以这一条的判据是：**棋盘自己会说的，我们不说；棋盘盖住了的，我们说。** 按这条线，
netslide/sixteen 的边框仍然不置灰（光标就在那儿摆着），而 cube 置灰——不是因为它算得出来而那
两个算不出来，是因为它看不出来而那两个看得出来。

**两道拒绝都要模型化，少一道就会留下亮着按不动的键：**

- **格子的形状**：下三角 `directions[DOWN] = 0`，上三角 `directions[UP] = 0`（cube.c:404、447）。
  三角网格上**永远恰好有一个上下键是死的**。这是看不见的那一道。
- **网格的边**：`find_move_dest` 找不到共边的格子就返回 -1（cube.c:1099），左右键也会撞上。

**实现在 `src/engine/cube.ts`，是推导不是副本**：位置每次从存档重新算（`CPARAMS` 给多面体和
维度，`DESC` 逗号后面是起始格，走子是 `L`/`R`/`U`/`D`），什么都不存。所以撤销、重做、重新开始、
恢复存档都不用单独处理——它们改的是存档，下一次读就看见了。读不懂就返回 null，四个键全亮，
也就是改之前的样子。

**坐标用整数，不是浮点。** 上游每个 x 都是半整数、每个 y 都是 √3/2 的整数倍，所以 x 乘二、
y 记成行号就完全精确，`find_move_dest` 里那个 `dist < 0.1F` 的近似比较也一并不需要了。

**代价是这里重写了一遍上游几何，而它会悄悄漂。** 检查在 `scripts/check-cube.mjs`，不在
`npm run build` 里（要浏览器和 playwright，和 `marks/`、三套图同一笔交易）。它把多面体深度优先
滚遍整张网格，**真值取自后端自己**——存档、发方向键、再存档，存档没变就是被拒绝了——**而断言
读的是按钮的 `disabled`**，不是模块的返回值，所以接线也一起测了。导航用的是另一份独立照着
cube.c 写的枚举，只用来决定往哪走，从不当作期望值。

实测：`c4x4` 16/16、`t1x2` 13/13、`o2x2` 24/24、`i3x3` 54/54，**107 格全部走到，零处不一致**。
**升级 `vendor/sgtpuzzles` 之后要跑这个**：模型漂了会把能按的键灰掉，而那是唯一一种读者报不
上来的故障——错灰的按钮和该灰的按钮长得一模一样。

**一个按钮只有一份工作。上游在某个局面下拿同一个键去干别的，按钮就置灰，而不是改行。**

**这条最初是 Sixteen 立的，而 Sixteen 后来把它推翻了一半。** 当时的说法是：光标走到边框上时那
两个键会推一行——一个实打实的动作——但按钮照样灭掉，因为推一行「不是它们的工作」。现在它们在
边框上换脸推行，因为「一份工作」不是我们定的，是**上游的这个键在这个位置上的意思**，而在边框
上那个意思就是推一行，棋盘还画着箭头替它说明。判据第三条那节记了这次翻案的全过程。

活下来的是 samegame 那一例，而且它才是这条规则真正的形状：站在孤立格子上、手里还有选中时，
上游给的是「取消选中」，而这个按钮的工作是「选一个区域，再按一次拿掉它」，一份工作两个步骤，
取消是第三件事。**读者站在孤立格子上，意思是他想选点什么而这里没得选**——那么一个写着「选中」
的按钮安静下来，正是这件事的样子。

**这条规则的另一面：blackbox 的 `Enter` 有四张脸，而那是对的。** 光标在三个区域各有一个含义
——角上是「检查」、场地里是「猜球／取消」、外圈是「发射」——看起来正撞上上面那条。分界线是
「这个键在这里干的事，是不是这个按钮的工作」：samegame 的「取消选中」不是（那是第三件事）；
blackbox 的四个**全都是**同一件工作
——把光标脚下这一格该做的事做掉——而且每一个都是光标站在那里时唯一可能的意思。**同一个键的
多张脸，看的是「它们是不是同一份工作在不同地方的样子」，不是数量。**

所以 `faces` 按钮的置灰规则比 `doesNothing` 那条更强，两条不要混：

- 普通键（Net 的旋转、五个铅笔键）：**标签说它什么都做不了**才灰。
- `faces` 键：**当前这个词不在它的脸谱里**就灰——哪怕按下去真的会发生什么。

而且灰的时候戴的是**自己的默认脸**，不是别人的脸。于是它说的是「这里做不了」，不是「这里我
变成了另一个东西」。实测在一盘 samegame 上带着选中扫过 49 个格子，按钮只出现过它自己那两张
脸，其中 4 格是灰的。

**抹空还能拿来判断「第二个键值不值得一个按钮」。** `lsk === csk` 时上游把 `lsk` 抹成空串，
所以 **`labels.space !== ''` 恰好等于「`Space` 干的事和 `Enter` 不同」**——不用比字符串，白送的。

samegame 就是这么定成单键的。它的四种局面里只有一种两个键不同：

```
未选中的区域      {Select, Select}      抹空 → 同一件事
已选中的区域      {Remove, Unselect}    ← 只有这一行不同
孤立格＋有选中    {Unselect, Unselect}  抹空 → 同一件事
没事可做          {"", ""}
```

而那唯一一行里 `Space` 独有的「取消选中」，玩下去一次都用不上：**光标移到另一个区域按一下就
直接换过去了**，因为那条分支是先清后选（samegame.c:1307，注释自己写着 "might be no-op"）。
实测两格的选中在一次按键里变成四格，没有产生任何走子。剩下的只有让状态栏那行
`Selected: n (p)` 消失，它不挡任何事。

**判据于是可以写得更准：第二个按钮要有资格，得在「相当一部分局面里」和第一个不同，而且那点
不同要真的有用。** 检查方法就是上面那一行。目前 40 个里 samegame 是唯一一个两条都不满足的，
rect 只在「开了拖拽还没动」那一瞬间两个键相同。

**亮 ≠ 安全，mines 是唯一一处这条有牙齿的地方。** `Enter` 在数字格上亮起来的条件是「周围旗数
等于这个数字」，而旗是玩家自己插的。插错了它照样亮、照样能按，按下去会把那一圈里真有雷的格子
挑出来翻开、`deaths++`（mines.c:2723）。那是这步棋本身的风险，点一下那个数字承担的完全相同
——我们没把事情变危险——但**一个亮着的按钮比一次点击更像一种背书**。以后再遇到「按钮亮起来
＝上游说这步能走」的情况，要分清「能走」和「该走」。

顺带一条实测得来的：**一个禁用的按钮仍然戴着它的默认脸。** 标签全空时（死了、赢了、光标没醒）
`faceOf` 回落到 `CursorKey` 自己的 `icon`/`says`，所以踩雷之后 `Space` 读出来还是「插旗，标记
为地雷」，只是按不动。写用例时别拿文案当「能不能按」的判据，那得问 `disabled`。

**「这个游戏还没有光标键」这条金丝雀退休了。** 用例里一直有一条断言，说某个还没做的游戏只有
四个箭头、旁边什么都没有；每做完一个就得换一个名字——mines、samegame、palisade、filling、
flood 都当过。四十个走完之后它没得可指了，于是反过来断言：**只剩 cube 和 fifteen 没有光标
键，而且是因为它们没有光标**（方向键本身就是走子）。

**图标要按渲染尺寸画。** 键是 40px 的方块、图标 20px。任何「环里套方块」的构图在这个尺寸下
会闭合成一个墨点——`rotate` 第一版就是这么废掉的。画之前先把候选并排渲染成 20px 亮、20px
暗、56px 三档来看。

**再加一条：这个按钮旁边就是四个箭头，所以图标不能长得像箭头。** pegs 那个键画的时候先试了
四个「说明方向键要动这枚棋子」的方案——一枚棋子加一个 chevron、一枚棋子四周围一圈 chevron
——20px 下它们在十字里读起来就是第五个箭头。另外两个把弯箭头压在棋子上的，20px 下是 redo
那个字形，而 redo 就在下面两行。最后选的是**把这个游戏的规则画出来**：两枚实心棋子加一个空
心孔，上面一道弧。它不像任何一个箭头，这就是它赢的原因。

**有一种按钮不做任何事，只是给方向键上膛。** pegs 是第二个（sixteen 的两个肩键是第一个）：
按下去只把 `cur_jumping` 置真，真正的走子是**下一次方向键**——pegs.c:960 把方向键那条分支
整个换掉，发出的是一步跳跃而不是移动光标。这类键的判据是第二条最干净的形态：它一步棋都不
产生，但没有它，这个游戏的方向键只能推着一个记号在棋盘上走。

它们的画法也和别的键不一样：**两张脸共用一张图**。识别一个按钮靠的是它的形状，而形状不能在
按下去之后变掉（sixteen 那节写过），何况 pegs 的棋盘自己就画着这个状态——光标停在棋子上时
整枚是光标色的实心圆，上了膛则变成一圈光标色的环套着棋子本来的蓝（pegs.c:1150-1155，实测
一盘新棋 3249 像素对 1214）。所以变的是词（上游给了 `Select` 和 `Cancel` 两个，第二个是新
消息：这一按是撤销）和 `data-on` 的底色。

**blackbox 的「检查」按下去之后光标会自己跑回场地。** `interpret_move` 在发出 `R` 之前写了
`ui->cur_x = ui->cur_y = 1`（blackbox.c:1258），所以按完检查，光标从左上角那个按钮回到场地第一
格，两个键随即换成场地那一对。猜对了则棋盘揭晓、标签闭嘴、两个键一起灭。写用例时别假设按完
检查还站在原地。

顺带一个够不着的上游小疤：**`current_key_label` 在角上无条件报 `Check`**，而
`interpret_move` 会再查一次 `CAN_REVEAL`。理论上存在「站在角上、球数又变得不够」的一刻，那时
按钮亮着但按下去什么都不做。走不到——方向键根本不让光标进那个角，而唯一能在光标不动的情况下
改变球数的是点棋盘，那会先把光标收起来。只有物理键盘按 `Enter`（那一下只负责把光标显出来）能
凑出来。不修，记在这。

**pegs 点空孔不会收起光标，只有点棋子才会。** 只有 `GRID_PEG` 那条分支写了
`ui->cur_visible = false`（pegs.c:898），点在孔上返回的是 `MOVE_NO_EFFECT`，光标原地不动、
棋盘也照画。所以「点一下棋盘按钮就该置灰」在这个游戏里只对了一半——写用例时按棋子点，别按
棋盘正中，因为十字盘正中恰好就是那个唯一的空孔。
