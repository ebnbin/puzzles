# 自定义参数的取值范围

Simon Tatham's Portable Puzzle Collection 四十个游戏的自定义参数面板里,全部 91 个 string 控件(上游 C_STRING)的取值范围:每一个的语义、上游 validate_params 的每一条规则(带源码行号)、本仓库最终给它的表、它看哪些别的控件、上限从哪来。choices 和 boolean 控件不在范围内,它们在上游本来就不是输入框。

**来源**:`vendor/sgtpuzzles/`,commit `3c3632259d298ab62aafa8a5858823569ab1af46`(2026-07-19)。全部规则直接读 C 源码得出;每条带 `文件:行号`,升级上游后照着重查。**代码是 SSOT**:范围写在各 `src/games/<game>.ts` 的 `types.params`,词汇在 `src/games/util/params.ts`;这份文档是索引和理由,不是第二份真相;它本身是生成物,手写源在 `scripts/lib/params-doc.mjs`,生成器 `scripts/build-params-doc.mjs`。两者是否一致由 `scripts/check-params.mjs` 对着上游源码验证(第七节)。

## 怎么读

分八节:**一、机制**是四十个游戏共有的那一层——值怎么进出 C、模型长什么样、控件怎么画、怎么把上游的量换成有语义的量;**二、总览**一张表横扫全部 91 个参数;**三、逐游戏详表**按上游收录序,每个游戏一节,列全该游戏的全部控件、每个 string 参数的语义与上游规则、本仓库的表、默认参数下模型算出的实际表、预设;**四、与上游的出入**;**五、被 CAP 封顶的参数**(还没定夺范围的清单);**六、已知问题**;**七、验证**;**八、实现**。

表里的「依赖」一栏写的是这个参数看谁:「主」= 不看别的数字参数;「看宽」= 表由宽算出,宽动了它可能被夹。

## 一、机制

### 1.1 参数从哪来、到哪去

类型面板一打开,宿主就向后端要一份 config box,参数列表常驻。C 侧 `game_configure` 给出一组控件,wasm 胶水(`engine/puzzle-lib.js`)只把三样交到 JS:英文 label、类型(string / choices / boolean)、当前值的字符串。没有 kw,也没有任何范围信息(`emcc.c:616-637`)。

提交时 JS 把每个控件的值原样交回(`dlg_return_sval`),C 侧 `custom_params` 用 atoi / atof / sscanf 解析成 `game_params`,再过 `validate_params(params, full)`。**自定义面板这条路 full 恒为 true**(`midend.c:2011`)——文中所有「full:」开头的规则都生效。不通过就把错误串回传显示成 Notice,box 保持打开;通过就开新局并重新要一次 box。

所以范围知识只能放在 JS 侧,而且只能按 label 认控件。

**预设与参数互相跟随**,两个方向都是上游算的:点一条预设时,C 侧只有一个 config box,所以宿主先让位(`dialogCancel`)、换参数(`selectPreset`)、再要一份——新的这份就是那条预设的值。反过来,每次参数落定后 `midend_set_config` 都会跟一次 `select_appropriate_preset`(`emcc.c:705`),它拿 `midend_which_preset` 按编码后的参数串逐个比对(`midend.c`),命中就报那条预设、不命中报 −1,界面照着它点亮「自定义」。所以选中态不是界面自己猜的。

常驻的这份 box 占着 C 侧唯一的那个位置:键区的偏好键要借同一个 box 用,借之前先让位、借完再要回来(`useConfigBox` 的 `borrowPrefs`),否则那一借会被静默丢掉。

### 1.2 范围模型

每个 string 控件在游戏文件里申报一条 `Param`:label、类型、一个函数 `allowed(read)`,输入其它控件的当前值,输出**升序的允许值表**。连续区间、偶数、约数、浮点等距取样、只有一个值(钉死)都是同一种东西:一张表。

**申报顺序即依赖顺序**:一张表只许看排在它前面的数字参数,以及任意 choices / boolean。排在前面的是「主」,后面的跟着让。所以宽高总是可以自由拉动,雷数、区域大小、旋转块边长这类派生量随之被夹。

**settle**:用户每动一个控件,宿主按申报顺序单趟走完所有表,值不在表内就吸到最近的表内值(等距取大),然后提交。表是按「后面的参数一定还有解」写的,所以走完必定是上游放行的组合;这条不变量由第七节的契约测试验证。

当前值来自上游(预设、Game ID、旧存档),可能在表外(比如 Game ID 里输入过 200×200,或 full=false 才放行的 2×2 Range)。面板先照实显示,滑块停在最近的一档;用户第一次动任何控件时才会被 settle 夹进表。

### 1.3 控件

**整数与浮点**:一个滑块,按表的**下标**走(表不连续也每一档都合法),两侧各一个 −/+ 步进按钮做精确微调,旁边显示当前值;表只有一个值时禁用。松手(change)才提交,拖动中只更新读数——和今天 checkbox / select 的「每次 change 即落定」一致。

**区间「a-b」**(只有 Black Box 的球数):同一个 label 下两行滑块,最少 / 最多;两者相等时写回单个数,和上游回显格式一致。

**附注**:两种。短的跟在读数后面(Mines 的雷数旁边显示占比,顶替下线的「20%」写法);长的在轨道下面单独一行(Rectangles 那一档由枚举算出来的 e)。读数列的宽度按当前这张表最宽的一条现算——宽度跟着值变的话,拖到一半轨道就缩水,滑块会从手指底下跑掉。

**兜底**:没申报的 string 控件(比如模态对话框那条路)仍画成文本框;label 对不上上游时申报被忽略,同样回落到文本框。

**上游那条「自定义」不画**:参数列表常驻之后它没有动作可做。参数不落在任何预设上时一条都不选中,那就是自定义。

### 1.4 上限的规矩

上游自身有上限的用上游的。上游没有的:网格维度封顶 100(棋盘最多 100×100 格),其它计数类参数先同用 100。第五节列出还没逐个定夺的那些——它们是占位,按游戏一个个读上游 + 实测来定。

几处故意与上游不同(补上游漏查的、或按语义封顶),全部列在第四节;契约测试把它们登记为「预期的收窄」,再多一处就 FAIL。

### 1.5 语义参数:把上游的量换成有语义的量

有些上游参数不是玩家能理解的量。Rectangles 的「扩展因子 e」是个没有上限的实数,但生成只通过 `(base_w, base_h) = (⌊宽/(1+e)⌋, ⌊高/(1+e)⌋)` 这一对整数看见它(`rect.c:1165-1168`):**落在同一对 base 上的 e 是同一个输入**,同种子下局面逐字节相同;而同一个 e 在不同棋盘上又是完全不同的粒度。这种参数值得在界面上换成它背后那个离散量。

四步(以 Rectangles 为例):① **找出真正影响生成的量**——把这个参数在上游源码里的每一次出现数一遍(`expandfactor` 共 11 处,只有 1165、1167 参与生成),看它经过什么变换进入生成,变换的像就是语义量。② **把语义量枚举出来,分界点用公式算**:`⌊边/(1+e)⌋ = k` 成立于 `1+e ∈ (边/(k+1), 边/k]`,分界点就是 `边/k`,两维并起来即全部;扫描是猜,公式才是证明,而且顺手能给出「一共几档」的闭式。③ **每个语义值反算一个上游认的原值当代表,再用同一套算法验回去**——代表值必须真的产出这个语义值,不验就等于假设。④ **控件里存的仍是上游的原值**:存档、Game ID、C 的回显只认它,语义值只活在界面和表里。

三条硬约束,都是踩到过的:**回显精度**——上游把值写回参数框用的什么格式(Rectangles 是 `%g`,六位有效数字),代表值必须能原样回来;回不来,下一次 settle 就把它当表外值,用户的设置被悄悄改掉。**算术要学像**——上游用 `float` 就得 `Math.fround`,截尾就得 `Math.trunc`;差一个 ulp 就会显示一个和引擎不一样的语义值(18×6 在 e = 0.2 处 `(float)18/1.2 = 14.999999`,base 是 14×5 不是 15×5,真机 DESC 也确实不同)。**表外的落点**——值不在表里时是吸到最近一档(`snap`,默认)还是回第一档(`reset`),按语义选;Rectangles 选 reset,因为换了棋盘整套枚举都换了。

**SSOT 是上游的原值**:它是唯一被持久化的东西(存档的 CPARAMS、Game ID、C 侧的 `game_params`);语义量是每次由别的控件现算出来的一张表,不落盘。两个方向不对称——`原值 → 语义值` 是全函数、和引擎逐位一致,任何值都算得出来;`语义值 → 原值` 是一对多里挑一个代表,只对枚举得到的那些语义值有定义。所以 `语义值 → 原值 → 语义值` 是恒等(表里每一档都是这么验出来的),`原值 → 语义值 → 原值` **不是**恒等,是一次规范化。跨棋盘更没有稳定性可言,也不该有:同一个原值在别的棋盘上就是另一个语义值。

附带一条:**枚举的算法算持久化契约的一部分**。改了代表值的取法(精度、候选规则),老存档里的原值可能落到新表外面——当前那一局不受影响(局面由 DESC 定),但面板一动就会被 settle 挪走。

**什么时候别做**:上游参数本身就有语义(宽、高、雷数、打乱步数)就别加这一层,加了只会让 Game ID 和界面对不上。

## 三、逐游戏详表

每节先列 config box 的全部控件(下标、类型、初值),再逐个说 string 参数。「默认参数下的表」是模型对着上游默认参数实际算出来的,和上一栏的描述应当一致。

#### `Width`(整数)

- **本仓库的表**:把 (base_w, base_h) 的每一种枚举出来,一对一档;写进控件的是算出来的 e。档数随棋盘变(7×7 六档、100×100 九十九档、100×99 一百九十五档 = 全局上限)
- **依赖**:看宽高;**上限来源**:本游戏自定;**控件**:滑块 + 步进
- **默认参数下的表**:{0, 0.166665, 0.399998, 0.749999, 1.33332, 2.5}

> **定下来的**:宽高 2..100(上限 100×100 是 owner 定的,和网格类参数同据:大屏桌面按长边算,100 格还认得出);扩展因子换成 base 对的枚举。下面几条是理由和实测。

> 宽高从 2 起是**避崩**,不是调优:上游只查 w·h ≥ 2,放行 1×n;但钳位那句写的是 `if (bw < 2 && w >= 2)`,宽是 1 时不触发,base 边长留在 0,扩展因子一动就死——真机上 1×7 往上加一档即 wasm abort(random.c:275 `bits < 32` 断言),之后连 midend_serialise 都断言失败。两维都 ≥ 2 时 base 必 ≥ 2×2,294 组抽样生成全过。

> 扩展因子的行为已逐条实测清楚:矩形个数只由 **base 面积**决定,与 base 形状无关(面积 16 时 4×4 出 7.1 个、8×2 出 7.6 个、16×1 出 6.8 个);e 只通过 base_w / base_h 两个整数影响生成(expandfactor 在 rect.c 里只出现在 1165、1167 两行),所以同一对 base + 同种子 = 逐字节相同的局面。跨棋盘对齐粒度的公式:想要 base b1×b2,则 e ∈ ( max(w/(b1+1), h/(b2+1)) − 1 , min(w/b1, h/b2) − 1 ],base 为 2 的那一维不参与上界(钳位让它到 +∞)。验证过 base 6×6 在 6×6 / 12×12 / 24×24 / 48×48 上矩形数都是 11.0–11.2。

> base 缩到最小(2×2)之后 e 再大也逐字节相同,那一点是 e > max(宽, 高)/3 − 1(边长掉到 2 需要 边/(1+e) < 3),100 宽的棋盘是 32.3。**e 因此是个跟着棋盘变的量**:同一个 e 在 7×7 上已经到底,在 100×100 上才走了 1/16。而且 e 只通过那一对 base 影响生成,**落在同一对 base 上的 e 是同一个输入**——真机验过:7×7 种子 #1,e = 0.2173 / 0.3 / 0.39 / 0.4 的 DESC 逐字节相同,e = 0.41 跨到 base 4×4 才换局面。上游自己也把 e 归为不持久的参数(encode_params 只在 full 时写它),等于承认它在 new_desc() 之后不再有意义。

> 所以面板上枚举的就是 **base 对**,一对一档,不再有连续的 e。档数由公式给出:`N = 宽 + 高 − 3 − C`,`C = max(0, gcd − j + 1)`,`j` 看 `min(宽/gcd, 高/gcd)`:等于 1 取 3、等于 2 取 2、≥ 3 取 1。(推导:`⌊边/s⌋ = k` 成立于 `s ∈ (边/(k+1), 边/k]`,所以一维的分界点是 `s = 边/k, k = 3..边`;`宽/k = 高/m` 当且仅当 `k = j·宽'`、`m = j·高'`。)短边整除长边(含正方形)时 N = 长边 − 1;互质且短边 ≥ 3 时 N = 宽 + 高 − 4。100×100 以内:最少 1(2×2)、最多 **195(100×99,唯一)**、平均 95.6,44% 的棋盘超过一百档。

> 每一档的 e 是算出来的不是扫出来的:两维的分界点 `1+e = 边/k` 并起来,每个分界点取到它下面最近的可表示值(区间左开右闭,往下取才落在里面;分界点本身和它下面一格都试,因为单精度除法正好落在分界点上时往哪边倒说不准),再按 e 递增对 base 对去重。全部 4950 块棋盘对过账:**没有一块比公式少**,19 块比公式多一档——那是上游单精度除法多切出来的一级,真机上确实是另一个局面(18×6 在 e = 0.2 处 `(float)18/1.2 = 14.999999`,base 14×5,DESC 与左右两档都不同)。另抽 398 块棋盘与密扫对账:不漏、严格递增、六位有效数字、无重复。

> **这一档的 SSOT 是 e**:存档的 CPARAMS、Game ID、C 侧的 `game_params` 里只有它;base 对是每次由宽高现算的一张表,不落盘。`e → base` 是全函数、和引擎逐位一致;`base → e` 是从一对多里挑代表。所以 `base → e → base` 是恒等(表里每一档都是这么验出来的),`e → base → e` 不是——`7x7e0.3` 落在 base 5×5 的区间里,而那一档的代表是 0.399998。今天连这一步规范化都不做:表外的 e 直接回第一档。要保住 Game ID 的意图,规则得改成「先按 base 对认,认不到再回第一档」。

> e 只能带六位有效数字:上游用 `%g` 把它回显进参数框(196),多了回来就变样,再落定时会被当成表外值。整数部分占几位小数就少几位,所以档位代表值最多六位小数。

> 换棋盘时表外的 e 一律回到第一档(e = 0,base 就是棋盘本身),不吸到最近的一档——整套枚举都换了,旧的 e 落在新表哪一档都没有意义。注意只改短边时,如果那个 e 在新表里仍然是某一档(长边的分界点没变),它会留在原地:范围模型只看得见「值在不在表里」,看不见「谁变了」。

> 耗时全部来自唯一解求解器,失败会把整局作废重生成,尾巴很长:原生 30 个种子,50×50 平均 0.28 秒最坏 0.75 秒,70×70 平均 1.84 最坏 6.29,100×100 五个种子平均 10.5 最坏 15.0。关掉「Ensure unique solution」后 100×100 只要 0.027 秒。

预设:7x7 `7x7`;9x9 `9x9`;11x11 `11x11`;13x13 `13x13`;15x15 `15x15`;17x17 `17x17`;19x19 `19x19`。

> `Barrier probability` 背后是个**整数墙数**:候选边 = 生成树用不到的边,而格子恒是一棵生成树(`宽×高−1` 条边),所以候选数是定值——不环绕 `(宽−1)(高−1)`,环绕 `宽×高+1`。公式推的,实测七组逐个对上(5×5=16、10×7=54、2×2=1、20×13=228;环绕 5×5=26、10×7=71、2×2=5)。也就是同一个整数墙数上的所有 b 是同一个输入,和 Rectangles 的 e 同类(见 1.5 节);这一轮维持 0..1 步长 0.01,与 Net 一致。上游还特意让墙的选取「加量不换旧的」:同种子下把 b 调大,新墙是旧墙的超集(616-624)。**墙越多越简单**——预设里 b=1 标 easy、b=0 标 medium、b=0 + 环绕标 hard(163-173)。

> 打乱程度实测(错位比例,20 个种子;约 90% 是随机基准——管形只有十几种,随机排列也会撞上一成):5×5 在 m=20 已到 81%、m=50 到 86%(默认 32 步是 86%);10×10 m=50 到 86%(默认 162 步 90%);50×50 m=100 到 70%(默认 4802 步 92%);100×100 m=100 只到 54%、m=500 到 85%(默认 19602 步 92%)。比 Sixteen 混得快得多——一次滑动就动一整行/列。

> 小盘不出事:2×2 只有一行一列可动(中心行列钉死),上游那个「被拒就重抽」的打乱循环在这种盘上照样终止(异侧方向的移动永远不会被判成撤销或重复)。2×2 / 2×3 / 3×2 各自加环绕、加满墙、m=1、2×100、100×2 环绕满墙,15 组 × 10 个种子全部正常返回。上游**没有** Net 那条「环绕 + 宽或高为 2 就拒」的检查(那是 Net 唯一解求解器的要求,Netslide 没有求解器)。

> Game ID 里 `wrapping` 和 `movetarget` 是持久参数(不带 full 也编码,251-254),`barrier_probability` 只在 full 时写(249)——和 Rectangles 的 e 同一待遇:上游认为墙的比例只在生成时有意义。

> 生成是**拒绝采样**(`generate_soluble`,667-726),一轮三步,任何一步不过就整轮重来、没有次数上限:① 造图(`generate`,251-343):每格一个随机数 → 一次 3×3 邻域平均 → 取**中位数**当阈值,正好一半格子涂黑;② **不许有整行或整列纯色**(686-713),但该维 ≤ 2 时跳过,上游注释:「otherwise nothing will ever be successfully generated」;③ **只靠单行单列推理就要能唯一确定**(`solve_puzzle`,510-665):反复调 `do_row` 推到不再变化,还剩一个 UNKNOWN 就算失败,不猜不回溯。所以耗时 = 每轮成本 ÷ 接受概率,而**两头各有一条判据会塌**。

> **失效方式一:短边小 → 死在第 ② 步。** 一行 w 格整行纯色的概率 q 实测:w=3 → 0.60、4 → 0.42、5 → 0.30、6 → 0.21、8 → 0.11、10 → 0.056、15 → 0.010、20 → 0.0017、≥25 → ~0。整盘要**每一行都不纯色**,概率 ≈ (1−q_短边)^长边:**底数由短边定、指数是长边,与面积无关**。3×30 只有 90 格,概率 5×10⁻¹³,跑满 300 秒不出结果;10×100 有 1000 格,概率 3×10⁻³,只要 0.1–0.5 秒。q 为什么这么大:一行 3 格若是独立抛硬币纯色概率只有 0.25,是那次 3×3 平均(上游**故意**抹出成片黑白块)加上中位数阈值把它抬到 0.60 的。上游的 `w > 2` 守卫等于承认这个问题,只是门槛定低了。(纯色行彼此不独立:每盘纯色行数的方差是二项分布的 1.4–1.6 倍,所以真实接受率比 (1−q)^h 高 3–200 倍,越稀有差得越多。)

> **失效方式二:面积大 → 死在第 ③ 步。** 求解器通过率随**面积**指数衰减、每轮成本只随面积线性长,实测 20×20 43%、30×30 10%、35×35 2.7%、40×40 0.27%、44×44 0.067%、≥46×46 一千五百轮零通过,拟合下来**面积每多约 100 格,耗时翻倍**(以 40×40 = 0.2 秒为锚,20×50、45×45、50×50 都对得上,散布约两倍)。

> 逐档实测(本机;owner 的机器快两三倍):5×30 = 0.17 秒、5×50 = 11 秒;6×46 = 0.53、7×46 = 0.015、8×46 = 0.007;20×50 = 0.011、30×50 = 0.15、40×40 = 0.20、40×50 = 6.2、44×44 = 2.0、45×45 = 2.7、46×46 = 8.4、47×47 = 13.4、48×48 = 44.7、**50×50 平均 >70 秒**(五个种子 15 / 42 / 76 / 116 / >120)。5 的倍数网格上 55 个组合里,除 45×50(约 18 秒,外推)和 50×50 外都在 11 秒以内。

> **顶格 50×50 是明知的代价**:本机平均 >70 秒、owner 的机器上 25–35 秒起,超过「20 秒」那条线,而且拒绝采样是几何分布、尾巴没有上界,生成期间页面是卡住的(同步跑在主线程)。owner 在看过这张表之后仍选择不设面积上限,理由是规则简单;要收的话最省事的一条是「面积 ≤ 2100」,在这个网格上正好只砍掉 45×50 和 50×50 两格。

> 下限 5 也是踩着悬崖定的:6×50 要 0.9–1.2 秒,5×50 要 11 秒(差十倍),4×50 与 3×30 直接跑不出来。上限 50 另有可读性一条:线索是文字,画出来是 `1.2×长边 + 4` 格(线索区 `TLBORDER(d) = d/5 + 2`,35、42-43),长边 50 时 1440×900 桌面上每格 14 px、线索字约 8 px,和 Fifteen / Sixteen 封 50 同一量级;长边 100 那种长条虽然生成只要 0.1 秒,每格只有 7 px、字 4 px,是被可读性砍掉的,不是被耗时。

> **耗时不落在「新游戏」上,落在第一次点击**:interactive 模式下 `new_game_desc` 只把随机种子编码进 desc(2065-2072),真正的布雷发生在点开第一格的时候(那一格决定安全区)。四十个游戏里只有这一个是这样。

> **成本 100% 来自「Ensure solubility」**:`minegen` 里勾着才走求解器 + 扰动 + 重开那条路,不勾就是随机撒雷一轮结束(1968)。实测同一组参数:100×100 撒 3500 / 4000 颗雷,勾着 >30 秒,关掉 **0.000 秒**;70×70、50×50 同样。

> **耗时是一条驼峰,峰在 40%**(不是密度越高越慢)。细扫:50×50 在 30% 是 0.059 秒、34% 4.19、38% 9.60、**40% 10.65**、44% 8.80、48% 3.96、54% 1.28;30×30 的峰也在 40%(1.56 秒)。满雷(面积−9)反而是瞬间的。按棋盘看:30×30 整条都安全(峰值 1.6 秒),50×50 峰值 10.6 秒,70×70 与 100×100 的 34–48% 段 >30 秒。

> 驼峰的成因在代码里读得出来,三条叠加:① 廉价推理只在「集合被填满或清空」时命中(`s->mines == 0 || == bitcount16(s->mask)`,846),一个有 k 个未知格的集合被一击判掉的概率是 `(1−p)^k + p^k`,k = 8 时 p = 0.2 或 0.8 都是 16.8%、p = 0.5 只有 0.78%,**中间最难**;② 开局的展开是低密度独有的红利——一格是 0 的概率 `(1−p)⁹`,10% 时 38.7%(点一下开半个盘)、40% 时只剩 1.0%,**这条只帮低密度**;③ 最强的全局雷数推理(937)有两级,`minesleft == 0 || == squaresleft`(1003)只在极端密度附近成立,而穷举所有集合不相交并那条被上游自己封在 `nsets <= lenof(setused)`、`setused[10]`(1026)——**集合超过 10 个就整条跳过**,大盘中密度时前沿很长、集合远多于 10,于是这条最强的推理根本不执行,高密度时反而跑得起来。②③ 都不对称,所以峰落在 40% 而不是 50%。推理断了就随机挑一个集合让 `mineperturb` 填满或清空(1220 附近),改不动就整盘重来(`do…while(!success)`,1865/1970,没有次数上限;试满 100 次后才允许大改,1946)。

> **100×100 配 30–50% 的雷是明知的代价**:本机 >30 秒,owner 的机器十几秒起,而且卡在**第一次点击**上。owner 看过上面这张表之后仍选择上限保持 100、雷数不设上限。要收的话最省事的一条是「长边 ≤ 50 时不限,长边 > 50 时雷数 ≤ 25% 面积」——50×50 的峰值(10.6 秒)正好卡在预算上,所以「长边封 50」等价于「雷数完全不用管」。

> 最小棋盘:勾着唯一解时是 **4×4**(本仓库的下限);上游自己允许到 3×4(面积 ≥ 10、两维 > 2),不勾时到 1×10 / 2×5。3×3 上游也拒——面积 9 时雷数上限成了 0,和「≥ 1」冲突。

> 百分比写法随文本框一起下线:滑块只出绝对数,旁边附「占比」读数;同样的雷数都能达到。上游那条 `custom_params`(266)只做换算不做钳位:9×9 输 `100%` 会被算成 81 颗然后被 `validate_params` 拒掉,不会自动降到上限 72;而 `90%` 因为整数除法截尾正好算成 72,反而放行。滑块没有这个坑。

预设:9x9, 10 mines `9x9n10`;9x9, 35 mines `9x9n35`;16x16, 40 mines `16x16n40`;16x16, 99 mines `16x16n99`;30x16, 99 mines `30x16n99`;30x16, 170 mines `30x16n170`。

> **定下来的**:宽高 2..100;色数上限统一封到 ⌊面积/2⌋;勾着「Ensure solubility」且宽 > 20 时色数下限抬到 4。「Scoring system」和「Ensure solubility」两个开关都留着,一个都不删。

> **宽高从 2 起**不是避崩:上游只查面积,1×n 能生成也不崩、还是瞬时。理由是机制退化——消完的复位是「先各列下落、再把空列整体左移」(`sg_snuggle`,1214),宽 1 永远没有列可移、高 1 永远没有格可落,两种都塌成同一个一维消除游戏。两维都 ≥ 2 之后面积恒 ≥ 4,不勾时那条「面积 ≥ 2×色数 ⇒ ≥ 4」自动满足,高的表也不用再看宽和开关了。

> **色数上限 ⌊面积/2⌋ 在勾着的时候同样成立,而且可证**:保证可解的生成器每次插两格(奇数面积开头有一次三格,24-26),所以整盘的块数恰好 ⌊面积/2⌋,能出现的颜色不可能比块多。实测在小盘上正好取等,一格不差(9 色、每格 3 个种子,数 desc 里的不同值):1×2 用 1 色、2×2 用 2、3×3 用 4、4×4 用 7、6×6 用 8–9、10×10 用 9。也就是说上游放行的那些高色数档在小盘上是死档,拖过去生成的还是同一种局面。

> **只有「三色 + 保证可解」会爆,其余整个 100×100 都是免费的。** 堵色那句是 `if (nwrong == nc) continue`(528),`nwrong` 是去重后的正交邻居颜色数,一格最多 4 个邻居 ⇒ **五色及以上永远堵不住,这是鸽笼不是统计**。实测:五色沿宽 = 100 那条边扫高 1..100,重来次数 ≤ 0.2;四色同样扫法 ≤ 8.5,整盒最坏出现在 100×100,0.21 秒(浏览器实测 0.17)。堵色概率也能算出来:邻居颜色独立均匀时,三色要 4 个邻居覆盖 3 个值 = 36/81 = 0.444,四色要 4 个邻居两两不同 = 24/256 = 0.094,五色起为 0(空格 0 也算一种「错色」,所以前沿更容易堵)。

> **三色的耗时有闭式**,两条律子相乘。① 重来是无记忆的:一轮里所有候选点都失败就 `n < 0` 整盘作废(837),`while (!ok)` 从空盘重开(864),不带任何状态 ⇒ `E[重来] = 1/P − 1` 是恒等式,上游自带的 `COUNT_FAILURES` 正好把它打出来。② 宽是唯一的指数轴,高不是:奇偶约束的条数 = 未满列的连续段数 ≤ **列数**(619-647 的扫描是 `for (i = 0; i < w; i++)`),与高无关。于是 `ln(E[重来]+1) = a·宽 + b`——高 20 时 a = 0.552、b = −1.111、**R² = 0.99935**(12 个点,宽 4..22,E 从 2.0 跨到 68302);高 100 时 a = 0.511、b = −1.245、R² = 0.995。**每加一列 ×1.7**。③ 单次尝试是 Θ(面积²)(每试一个候选点都 `memcpy` 整盘,438;轮数 Θ(面积)),实测 **1.22×10⁻⁹ × 面积² 秒**,九个点(面积 2500..10000)误差 5% 以内,且只看面积(100×20 和 20×100 同值)。合起来 `T = (1 + e^(a·宽+b)) × 1.22×10⁻⁹ × 面积²`,和独立测的墙钟对得上:高 100 时宽 12/14/15/16 预测 0.23/0.89/1.70/3.22,实测 0.24/0.84/1.59/3.19,浏览器(wasm)0.37/0.81/1.14/5.93 —— wasm 和原生同量级。四色的同一条律子 a 只有 0.022(高 10),差 25 倍,这就是三色和四色的分水岭。

> **宽 20 是 owner 定的,明知代价**:三色宽 20 的实测(每点 5 个种子,本机比 owner 的机器慢 2–3 倍)——20×15 平均 3.4 秒、20×20 4.5、20×30 7.0(最坏 25.8)、20×40 15.8(最坏 37.4)、20×50 38.1(**最坏 111**)、20×75 9.1、20×100 16.7。重来次数服从几何分布,尾巴很长,单局波动比这张表大。要收的话按公式解出来的曲线是:高 ≤ 20 给到宽 20、高 50 给到 17、高 100 给到 16,那样任何组合都在 5 秒内;owner 选了平的 20,接受高盘慢。15 那个值另有一条好处:正好保住上游最大的三色预设 15×10c3。

> **可读性**:这个游戏没有数字也没有网格线,唯一的视觉分隔是块间那道缝,而缝宽 `tilegap = (格边长 + 8) / 16` 是整除(1360)——**格边长 < 8 px 时缝宽变 0,块的边界直接不画**。实测每格像素:1440×900 上 30×30 是 24.7、50×50 是 14.3、80×80 是 9.1、100×100 只有 **7.1(无缝)**;2560×1440 上 100×100 是 12.1(有缝);390×844 手机上 50×50 就 7.1 了。按「大屏桌面为准」100 仍然过关,但笔记本屏上的 100×100 会掉到没有缝那一档;真要对得起小屏,临界点是 90。

> **「Ensure solubility」是两种玩法,不是一个生成质量开关**(所以留着)。勾着 = 谜题:目标是清空(`game_status` 只在 `complete` 时判胜,1638),盘面碎;不勾 = 街机(原版 Chain Shot):`gen_grid_random`(893)一遍撒完,块大一倍。实测(每格 30 个种子,先 400 次随机试走证「能清空」,再穷举证「不能」):10×10c3 平均最大块 5.4 对 11.0、贪心得分 168 对 472;**五色起随机盘基本清不空**——5×5c5 只有 4/30、8×8c8 是 0/30(14 局证否,贪心打完平均还剩 30.7 / 64 格),而保证可解那侧「证否」恒为 0。街机模式还是 2 色唯一的去处(勾着时上游硬性要求 ≥ 3)。

> **「Scoring system」只作用于记分**(所以也留着):`scoresub` 唯一的使用点是 `npoints`(129),只被 `execute_move`(1343)和状态栏(1596)调用;两个生成器一次都没读过它。实测同种子换计分法,desc 逐字节相同。区别只在最小的那一步:`(n-2)²` 下消两格得 0 分,而出题机器的解全程都是两格步 ⇒ **机器的解正好得 0 分**(奇数面积得 1,那一次三格步),玩家的分数字面上就是「比机器强多少」——上游注释 33-37 就是这么说的,实测限制只走两格步,5×5c3 十五个种子全部清空得 1 分、6×6c3 与 6×6c4 全部得 0 分。`(n-1)²` 没有这个零点(机器的解就能白拿 面积÷2 分),而且**分辨力更差**:同一批盘面,「200 次试走里最好的一条」比「随机走一条」拉开的倍数,`(n-2)²` 是 2.86/3.27/3.32/2.89(10×10 的 3/5/9 色、15×10c3),`(n-1)²` 只有 2.33/2.07/1.70/2.38 —— 它给每一步都加底分,把好坏差距摊薄了。顺带:每次都消最大的块得分反而更低(10×10c3 贪心 168、随机 237),这个分数是有本事含量的。

预设:5x5, 3 colours `5x5c3s2`;10x5, 3 colours `10x5c3s2`;15x10, 3 colours `15x10c3s2`;15x10, 4 colours `15x10c4s2`;20x15, 4 colours `20x15c4s2`。

> **这个游戏的成本是面积的平方,而且只看面积。** 矩阵是 `wh × wh` 字节(365),而 `new_game_desc` 把它整个 hex 编进描述(596-600,两种模式都编),所以 **DESC 长度 = ⌈面积²/4⌉ + ⌈面积/4⌉ + 2** 个字符,里面没有宽高单独出现的位置。实测面积 400 的七种形状(20×20 / 10×40 / 40×10 / 8×50 / 50×8 / 4×100 / 100×4)DESC 全是 40 102 字符,一字不差;Crosses 的耗时同理只看面积(面积 2500 的 50×50 / 25×100 / 100×25 是 0.018 / 0.017 / 0.018 秒)。

> **DESC 落在三个地方**:存档(`puzzles.save.flip`)、菜单里那行「游戏 ID」(直接渲进 DOM)、React state。对比同样 50×50:Mines 的 DESC 是个随机种子(二十来字符)、Same Game 是每格一个颜色号(5 000 字符)、**Flip 是 1 563 127 字符**。浏览器给一个站的 localStorage 约 5 MB 且全 app 共用,而 `writeSave` 是静默吞异常的——超了不报错,只是这一局重开就没了。实测:面积 3200(64×50,256 万字符)写得进但正好吃光配额,面积 3364(58×58)起 QuotaExceededError。菜单打开耗时:面积 900 是 76 ms、2500 是 398 ms、3600 是 1 228 ms、10000 是 **9 559 ms**。

> **Random 模式的生成耗时随面积指数涨**,Crosses 不涨。Crosses 是纯 Θ(面积²):浏览器里面积 1600 只要 57 ms、面积 10000 也只要 1 291 ms。Random 是拒绝采样——加完格子后要求「没有两行完全相同」,否则整个重来,没有次数上限(508-524,上游注释自己预测了这个 scalability 问题)。合起来 **T ≈ 4.3×10⁻⁷ × 面积² × e^(0.00345×面积) 秒**,两个系数只用面积 400 和 900 两点定,其余全是留出来验证的,原生实测(多种子平均):面积 100 → 0.012、200 → 0.031、400 → 0.22、600 → 0.95、800 → 4.8(最坏 11.8)、900 → 5.6(最坏 14.5)、1000 → 14.8(最坏 42.5)、1200 → 50.9(最坏 150)、1400 → 93.5(最坏 271)、1600 → 231.8。公式在这些点上偏差 ≤ 1.7 倍。同面积 1600 时 Crosses 是 57 ms,**差 4 万倍**。

> **形状只在极瘦时才有影响,幅度远小于面积项。** 面积 400 的实测(20 个种子):20×20 0.26、40×10 0.23、50×8 0.29、80×5 0.45、100×4 0.79、200×2 >30 秒、**400×1 只要 0.004 秒**。机制:Random 要加 `4×面积 − 2(宽+高)` 个格子,可加的候选有 `(3宽−2)(3高−2) − 面积` 个,两者一减正好是 **余量 = 4×(宽−1)×(高−1)**——这是生成器的自由度。余量占「要加的量」的比例:20×20 是 95%、100×4 是 85%、200×2 是 66%、1×n 是 **0**。余量越薄越容易撞上重复行;而短边 = 1 反过来最快,因为余量归零、矩阵被完全钉死,没得选也就没得拒。定下来的范围里最瘦的 40×2 只要 0.07 秒。

> **宽高从 2 起是避挂,不是调优。** 1×n 的余量正好是 0 ⇒ 矩阵被钉死,加出来必然就是十字矩阵(实测 1×3 / 1×4 / 1×5 / 1×8 / 1×20 / 5×1 换种子都和 Crosses 逐字节相同,**1×n 的 Random 根本不随机**);而 1×2 的十字矩阵两行相同,撞上「不许两行相同」⇒ **永远重来,死循环**。四个种子基各跑 15 秒都不出,与种子无关。宽高 1..8 的 48 个组合全扫过,只有 1×2 和 2×1 会挂;抬到 2 之后又把宽高 2..12 的 121 种棋盘 × 两种模式 × 各 2 个种子(242 组)跑了一遍,零出错。

> **上限 50 / 面积 1000 是 owner 定的,明知代价**:面积 1000 时 Random 平均 14.8 秒、最坏 42.5 秒,浏览器里抽到过 59.7 秒(这个分布尾巴极长,均值和单局体感差很远)。我的建议是面积 800(平均 4.8 秒)。存档那头面积 1000 只占 5 MB 配额的 10%,很宽裕——Crosses 单独看其实能到面积 1600–2500,owner 选了两种模式同一套。

> **格子里有信息,32 px 以下就糊了**:每格要画一张小图标出「按下去翻哪几格」(1152-1170),小图的格边长 `td = TILE_SIZE / 16`(不足 1 取 1),**td = 1 时退化成一坨 2 px 方块**。td ≥ 2 需要格边长 ≥ 32 px:2560×1440 上边长 ≤ 38、1440×900 上 ≤ 21、390×844 手机上 ≤ 11。Crosses 模式这张图是废话(永远是十字),Random 模式它是唯一能知道一次点击做什么的信息。边长封 50 没有卡在这条上——面积 1000 时方盘只有 31×31。

> **这个游戏没有生成成本,也没有任何危险组合。** `new_game_desc` 是 O(钉数) 一遍过;唯一的重挑发生在不勾「Allow duplicates」时(`goto newcol`),而那时上游保证颜色数 ≥ 钉数(227),期望次数是 n·H(n)——10 钉也才 29 次。真机极端组合 **10 色 / 100 钉 / 100 次:落定加画完 614 ms,零报错**;最小 2 色 / 2 钉 / 1 次同样正常。所以上限完全是可读性和游戏性的事。

> **布局是一条线性式子**(1029-1053,常数在 1025-1027:BORDER 0.5、PEG_GAP 0.10、PEG_HINT 0.35):`画布宽 = 钉边长 × (2.9 + 1.1×钉数 + 0.45×⌊(钉数+1)/2⌋)`、`画布高 = 钉边长 × max(0.9 + 1.1×颜色数, 2.1 + 1.1×次数)`。两个轴分开:宽只看钉数,高只看「颜色数和次数的较大者」。钉子里那个数字用 `PEGRAD` 当字号 = **钉边长的一半**(1254),右边的提示点是 0.35 倍。1440×900 实测(画布约 1412×700):20 钉 48 px、30 钉 33、50 钉 20、100 钉 10;次数 10 是 53 px、20 是 29、30 是 20、50 是 12、100 是 6。手机 390×844 上 10 钉 24 px、15 钉 16 px。

> **要几次才猜得出来:99 个格子实测。** 两套独立解法互相对过表——空间 ≤ 130 万时枚举全部密码跑「随机一致」和「最小最大(Knuth)」两种策略(6 色 4 钉上强玩法平均 4.5 / 最坏 6,和文献已知最优平均 4.476 / 最坏 5 对得上);空间更大时用局部搜索找一个与全部历史反馈相符的密码来猜,在 6 色 4 钉和 10 色 6 钉上与枚举法一致。**「随机一致」的平均次数**(色数 × 钉数):2 色:钉 4 → 2.9、10 → 5.4、20 → 9.1、**50 → 17.3**;6 色:4 → 4.7、10 → 8.0、20 → 14.3;10 色:4 → 6.1、10 → 9.9、20 → **16.0**。不勾「Allow duplicates」时 10 色 10 钉是 11.0(最坏 14)。

> **次数的公式**(99 个实测点,R² = 0.978,最大偏差 2.0 次):`平均次数 ≈ 0.1 + 0.96×log₂(颜色数) + 钉数 × (0.24 + 0.12×log₂(颜色数))`——每多一个钉子加 (0.24 + 0.12·log₂色) 次,2 色时每钉 0.36、10 色时每钉 0.65。外推到 50 钉验证过一次:2 色 50 钉公式 19.3、**实测 17.3**(最坏 18)。按它算 10 色 50 钉要 **36 次**、6 色 50 钉 31 次。顺带:信息下界(⌈钉×log₂色 / log₂((钉+1)(钉+2)/2−1)⌉)完全不能当参考——它说 2 色 20 钉只要 3 次,实测 9 次;10 色 20 钉它说 9 次,实测 16 次。反馈分布远不均匀,那个上界拿不到。

> **50 / 50 是 owner 定的,明知代价**。可解性上没问题:10 色 50 钉平均 36 次,50 次给到 1.4 倍富余,而且钉数越多分布越窄(平均与十来局里最坏的差:6 色 20 钉 1.7、10 色 20 钉 1.0、2 色 50 钉 0.7),最坏大概落在 40 上下。代价在可读性:**50 钉 × 50 次时钉边长只有 12.3 px、数字 6.1 px、提示点 4.3 px**,而提示点是这个游戏唯一的信息来源(右边是 25 列 × 2 行的点阵)。另外一局要点约 1800 下(36 手 × 50 个钉子)。我的建议是钉 20 / 次数 30(钉边长 20 px、提示点 7 px,最难的角落仍有 1.9 倍富余)。

> **Random 是拒绝采样,而且拒绝的理由是几何的。** `pegs_generate` 从中心一颗棋子反向走子长出一片,然后要求这片**四条边都够到**(`extremes == 15`),否则整盘重来,**没有次数上限**。把 `pegs_genmoves` 单独抠出来跑(把 pegs.c 整个 include 进一个探针,不动 vendor 一行)量出三件事:① 那一片的**面积恒是盘面的 57%**——`nmoves < 面积/2` 之后就不再接受代价 2 的走子(1148),实测从 10×10 到 100×100、从方盘到细条全是 57%;② 它是**团状**的(生成器优先走代价 0 的子,紧凑铺开,不长细胳膊);③ 于是细长盘上它很快把短边顶满,之后只能横着长成带子,带宽 ≈ 0.57×面积 ÷ (0.87×短边) = **0.66×长边**——**永远够不到两头**。包围盒实测(每格 200 次):100×100 是 94.9×95.4(长边 95%);20×10 是 17.4×**10.0**(87%);30×10 是 24.1×10.0(80%);100×10 是 66.2×**10.0**(**66%**);100×50 是 77.4×50.0(77%)。短边那一列永远顶满,长边永远差一截。

> **通过率**(两万次尝试)。方盘:4×4 86%、10×10 36%、20×20 24%、30×30 15%、50×50 6.0%、100×100 1.0%——大约按 面积^−0.78 掉,所以 100×100 平均要重开一百次、耗时 2.87 秒(浏览器 1.39 秒)。细长盘直接掉到零:**50×4 到 50×15 全是 0/20000**;能量到的最差有限值是 50×20(通过率 1/10000,真生成器实测平均 29.7 秒、最坏 54.9 秒),50×25 是 4.62 秒,50×30 才回到 0.24 秒。这一整片今天在 4..100 的表里都点得到:100×10、10×100、100×50、50×100、100×4、4×100 各跑 300 秒,一个都没出来。

> **上限取 30 之后不再需要额外的长宽比规则**,因为 30 以内最瘦的组合还撑得住:真生成器实测(每格 20 个种子)30×4 平均 1.60 秒最坏 7.37、4×30 平均 1.89 最坏 5.96、30×5 平均 1.81 最坏 9.50、30×6 平均 1.60、30×8 平均 0.61、30×10 平均 0.31、30×30 平均 0.015。要再收的话「|宽−高| ≤ 20」会把最坏从 1.8 秒压到 0.44 秒,但没有必要。(如果哪天上限抬回 50,那条长宽比规则就是必需的——50×15 及更瘦的组合根本打不开。)

> **要走多少步 = 面积 ÷ 2。** 反向每走一步净加一颗棋子(拿掉 1 颗、放上 2 颗),而生成停在 面积/2 步附近,所以棋子数 ≈ 面积/2 + 1;胜利条件是「场上只剩一颗」(1039-1045),于是步数 = 棋子数 − 1。真机实测:7×7 Cross 32 颗 / **31 步**(这就是经典孔明棋)、10×10 51 颗、20×20 202 颗 / 201 步、30×30 453 颗 / **452 步**、50×50 1252 颗、100×100 5001 颗 / **5000 步**。上游自己的 Random 预设最大只到 9×9。30 这个上限对应 452 步,已经是经典孔明棋的 15 倍。

> **可读性**:棋盘 = 一格 × (宽+1) × (高+1)(1069),棋子是纯色圆点、没有文字,但操作是「先点一颗棋子,再点两格之外的落点」,对点击精度的要求比「点一片」高。1440×900 真机:10×10 是 64.9 px、20×20 是 35.0、**30×30 是 24.0**、50×50 是 14.0、100×100 是 7.0。

## 六、已知问题

- 本文档里的耗时数字全部测自一台共享的 2.8 GHz Xeon(开发容器),比现代桌面 CPU 慢两三倍——同一组参数 owner 在自己机器上实测能快到三分之一。逐个游戏定范围时按这台机器的数字取,偏保守。
- 生成是同步跑在主线程上的:参数越大,`midend_new_game` 卡住页面的时间越长,滑块一滑到底就能撞上。还没定夺范围的游戏只记录,不为耗时调低上限。已知的重灾区:Loopy(尤其 Penrose / Hats / Spectres 网格)、Solo 高阶(31 阶 Unreasonable 几乎不会结束)、Untangle 100 点、Map 大盘多区域、Bridges / Tracks / Galaxies 100×100。
- Mines 是唯一一个耗时不落在「新游戏」上的:布雷发生在**第一次点击**。100×100 配 30–50% 的雷本机 >30 秒,owner 看过实测后仍选择上限 100、雷数不设上限——那一下卡的是点击,不是开局。
- **已定夺的游戏里 Pattern 是唯一一个仍会明显卡顿的**:顶格 50×50 本机平均 >70 秒(owner 的机器 25–35 秒起)。owner 看过逐档实测后仍选择不设面积上限,取规则简单;要收的话「面积 ≤ 2100」正好只砍掉 45×50 和 50×50 两格。
- 页面卡在生成里时,存档不会写坏:重开页面恢复的是上一局(存档按序列化的局面存,不重新生成)。但「新局」会再生成一次,同样卡。
- 每次松手都开一局:在滑块上用方向键连按,每按一下都生成一局。
- 另一类不是「大」而是「小到无解」的不终止:浏览器探测到 Light Up 3×3、黑格 5%、4 向旋转、难度 Tricky / Hard,Galaxies 3×3 Unreasonable,Solo 2×2 Killer + X,上游生成器死循环重试(lightup.c:1558、galaxies.c:1456)。这几处上游放行、表也放行,还没定夺的先只记录;二阶 Solo 配对称 / Killer 与 Penrose 最小尺寸那几处因为一碰就死,已按第四节收窄。
- Solo 勾了 Jigsaw 之后,行数滑块每拉一档阶数就翻倍(上游语义,C 侧把两数相乘)。表允许,因为上游允许;要不要在界面上钉住行数,等定 Solo 的范围时再说。

## 七、验证

`scripts/check-params.mjs`(何时跑见文件头)把 `vendor/` 的 C 源码和 `scripts/lib/params-oracle.c` 用 gcc 编成 40 个 oracle,不动 vendor 一行,也不生成棋盘,直接调 `custom_params` + `validate_params(full=true)`。对每个游戏做三件事:

1. **覆盖**:每个 string 控件都有申报,每条申报都能按 label 认到控件。
2. **健全**:choices × boolean 的全部组合(超过 96 种抽 96 种)下,按申报顺序把每张表走一遍(大表抽两头、等距、随机共 14 个),走出来的每个组合上游都放行;路上没有空表;settle 对表内组合是 no-op;另从随机乱值出发 settle 之后上游也放行。
3. **紧**:表外一格(下界减一、上界加一、表中间的洞)按界面做法钉住、后面的参数照 settle 落定,上游若放行就是「比上游窄」——只有第四节登记过的算预期。

## 八、实现

范围模型落地为控件,动到的文件:

- `src/pages/puzzle/ParamField.tsx`:范围模型驱动的数字行。滑块按表的下标走,两侧 −/+ 单步,读数在行尾;区间型两行(最少 / 最多)。拖动只改读数,原生 change 才落定,方向键每按一下落定一次。
- `src/pages/puzzle/ConfigFields.tsx`:拿到范围模型后,有申报且表非空的 string 控件交给 ParamField;每次落定(滑块、步进、checkbox、select、回落的文本框)先 `settle` 再提交。没给模型的调用方(偏好面板、模态对话框)行为不变。
- `src/pages/puzzle/PuzzleTypes.tsx` / `PuzzleHost.tsx`:把当前游戏的 `types.params` 传进面板;参数列表常驻,选中态只认引擎报的那条预设(不命中就一条都不选),点预设走「让位、换参数、再要一份」三步。
- `src/ui/Dock.tsx` / `useMedia.ts`:够宽的桌面上类型面板停靠成右侧栏(360px),棋盘让出宽度而不是被盖住;非模态,面板开着照样能走子。
- `src/index.css`:`.sheet-custom .dialog-param*`,颜色全部走 tokens,两种主题同一套规则。
- `src/i18n/en.json` / `zh.json`:`types.min` / `max` / `decrease` / `increase` 四个键(区间小标与步进按钮的读法)。
- `scripts/check-custom.mjs`:playwright 走真实链路——四十个游戏的自定义面板没有文本框、动一档即开新局、Mines 缩到最小雷数被夹、Twiddle 宽降到 2 旋转块跟着降、Black Box 最少拉过最多时最多跟上、Mines 翻 Ensure solubility 时宽从 1 回到 3、步进按钮加一,全程不出错误 Notice。
- `scripts/build-params-doc.mjs`:本文档的生成器,手写源在 `scripts/lib/params-doc.mjs`;第七节的结果表每次生成时当场跑 check-params 得到。
